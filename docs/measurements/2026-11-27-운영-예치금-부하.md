# 운영 예치금 부하 측정 (2026-11-27 새벽)

운영 서버(`crewrun.duckdns.org`, 2 vCPU 한 대 + 데이터 서버)에서 예치금을 처음 쟀어요. 1·2차는 맥의 컨테이너에서 쟀어요.
두 부분으로 나눠 쟀어요.

- **1부**: 충전이 섞인 실제 예매 흐름(real-flow, CRU-110)
- **2부**: 충전 한계(`charge-ramp.js`)

## 1. 한 줄 결론

- **돈은 두 부분 모두 맞았어요.** 1부는 결제 208건과 충전 47건, 2부는 충전 4,026건이었고, 이중 결제·중복 충전·잔액 끊김이 모두 0이에요.
- **예치금 서버 안은 빨랐어요.** 예매 흐름 속 예치금 결제는 p99 771ms예요. 기준인 1초 미만을 통과했어요. 충전은 초당 80건 단계까지 p99 879ms였고, 이 값에는 가짜 토스 지연 500ms가 들어 있어요. 예치금이 거절한 요청(429·503)은 0건이에요.
- **사용자가 겪은 시간은 기준을 넘었어요.**
  - 1부: k6 기준 조회 p95 4.8초, 쓰기 p95 2.8초. 11/20처럼 화면(Next) 렌더링이 먼저 막혔어요.
  - 2부: 충전 p99가 5초를 넘어, 초당 80건 단계 20초 만에 자동으로 멈췄어요.
  - 게이트웨이 1까지의 충전 평균은 598ms로 예치금 안(583ms)과 거의 같았어요. 그래서 늘어난 시간은 예치금 밖에서 생겼어요. nginx, 게이트웨이 2, 네트워크, 부하를 보낸 맥 중 어디인지는 나누지 못했어요.
- **측정 대상이 아닌 곳에서 하나 찾았어요.** 테스트 계정을 50명씩 동시에 가입시키자 **회원 서비스가 메모리 한도(640Mi)를 넘어 강제로 종료됐어요**(01:40, OOMKilled). 10명씩으로 줄여 가입을 마쳤어요.

## 5. 2부: 충전 한계 (충전 초당 10 → 20 → 40 → 80건, 단계당 45초)

- 초당 80건 단계 20초째(시작 2분 35초)에 충전 p99가 5초를 넘어 **자동으로 멈췄어요**.
- 맥의 k6가 가상 사용자 600명을 모두 쓰고도 목표 속도를 못 따라가, 반복 522번을 버렸어요(`dropped_iterations`).

| 응답 시간 | 건수 | 평균 | p95 | p99 |
|---|---|---|---|---|
| 충전 확정 (예치금 서버) | 4,026 | 583ms | 733ms | 879ms |
| 충전 확정 (게이트웨이 1까지) | 2,003 | 598ms | | |
| 충전 확정 (k6) | 3,861 | 1,040ms | 3,520ms | 5,290ms |
| 잔액 조회 (예치금 서버) | 3,796 | 15ms | 43ms | 157ms |
| 내역 조회 (예치금 서버) | 3,680 | 33ms | 93ms | 202ms |
| k6 조회 전체 | 7,343 | 410ms | 2,840ms | 4,230ms |

- 실패 0건. 동시 처리 100개 초과(`CHARGE_BUSY`)와 남용 방지 쿨다운 429도 0건이에요. 예치금 안에서 동시 충전이 100개에 닿지 않았다는 뜻이에요.
- 예치금 서버 충전 4,026건과 k6 완료 3,861건의 차이(165건)는 자동 멈춤 때 k6가 응답을 받기 전에 끊은 요청이에요. 서버에서는 모두 완료됐고 돈도 맞아요.
- 끝난 뒤 DB 연결 대기(`hikaricp_connections_pending`)와 연결 시간 초과는 0이었어요. 측정 도중의 시계열은 남기지 못했어요.
- 돈 확인(`check-charge.sql`, 앞머리 `charge-cr-mwxtt2m6-`)
  - 충전 4,026건 모두 완료, 40,260,000원
  - 원장 두 줄 0
  - 상태와 원장 불일치 0
  - 잔액 끊김 0
  - 마지막 원장과 잔액 불일치 0

**충전 한계**: 단계별 숫자를 따로 남기지 못해서, 어느 단계에서 기준을 처음 넘었는지는 **판정하지 못했어요**. 확실한 것은 두 가지예요.
- 초당 80건에서 사용자 쪽 p99가 5초를 넘었어요.
- 그때도 예치금 서버 안은 p99 1초 아래였어요.

## 6. 한계

- 단계마다 1회 측정이에요.
- 부하를 맥북 에어 한 대에서 집 네트워크로 보냈어요. 2부에서는 맥 쪽이 목표 속도를 못 따라갔어요(`dropped_iterations` 522).
- 가짜 토스 승인 지연 500ms는 실제 토스를 잰 값이 아니에요.
- 예치금·게이트웨이 숫자는 끝난 뒤 찍은 누적값의 차이예요. 시간에 따른 그래프와 단계별 값이 없어요.
- 게이트웨이 2(보조 EC2)를 지난 요청의 시간은 보지 못했어요.
