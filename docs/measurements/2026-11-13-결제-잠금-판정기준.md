# 주문 결제 잠금 측정: 판정 기준과 시나리오 (2026-11-13)

결제(`OrderPayUseCase`)는 주문·참가 신청·키트 옵션 판매 수를 잠근 채 예치금 결제 HTTP와 상품 자리 판매 HTTP를 불러요.
이 구조를 「결제 중」으로 먼저 커밋하고 잠금 밖에서 HTTP를 부르는 구조(C안)로 바꾸기 전에, 같은 조건에서 변경 전(A)과 변경 후(B)를 재요.
이 문서는 **측정 전에** 커밋해서, 숫자를 보고 기준을 바꾸지 않게 해요.

근거 없이 고른 값에는 「추천값(미확정)」을 붙였어요.

## 1. 판정 기준

### 변경 전(A)을 「문제 있음」으로 보는 조건 (하나라도 맞으면)

| 번호 | 조건 | 값 |
|---|---|---|
| P1 | S4(예치금 0.3초 지연, 종목 5개 흐름)에서 주문 DB 연결을 기다리는 요청(`hikaricp_connections_pending`)이 0보다 큰 상태가 30초 넘게 이어짐 | 30초 추천값(미확정) |
| P2 | 같은 조건에서 결제 p95가 2초를 넘음 | 2초 추천값(미확정) |
| P3 | 같은 조건에서 결제 실패(2xx가 아닌 응답)가 1%를 넘음 | 1% 추천값(미확정) |
| P4 | S3(같은 키트 옵션 20명 동시 결제)의 결제 p95가 S2(옵션이 모두 다름)의 p95보다 3배 이상 | 3배 추천값(미확정) |

평소 속도(S1)에서 위 조건이 하나도 맞지 않으면 「평소엔 괜찮고, 예치금이 느려질 때만 위험」이라고 그대로 적어요.

### 변경 후(B)를 「나아짐」으로 보는 조건 (모두 맞아야)

| 번호 | 조건 | 값 |
|---|---|---|
| G1 | S4에서 연결 대기 최대값이 A보다 50% 이상 줄거나 0 | 50% 추천값(미확정) |
| G2 | S3에서 결제 p95가 A의 절반 이하 | 절반 추천값(미확정) |
| G3 | 모든 시나리오에서 실패율이 A보다 높지 않음 (차이 0.5%p 안은 같다고 봄) | 0.5%p 추천값(미확정) |
| G4 | 아래 정확성 확인이 모두 통과 | |

### 정확성 확인 (A·B 모두, 반복마다 측정 끝에 SQL로)

| 번호 | 확인 | 통과 조건 |
|---|---|---|
| C1 | 돈 합계: 측정 회원 지갑 + 보관 지갑(2번) + 수수료 지갑(1번) 잔액 합 | 시작 때와 같음 |
| C2 | 이중 차감: 주문 하나에 `사용__주문결제` 장부 줄이 2줄 이상 | 0건 |
| C3 | 상한 초과: 키트 옵션 판매 수 > 준비 수량 | 0건 |
| C4 | 개수 맞음: 결제 완료 주문 수 = 예치금 결제 완료 수 = 판매된 자리 수 | 세 값이 같음 |
| C5 | 멈춘 결제: 예치금 결제는 완료인데 주문이 결제 완료가 아닌 것 (B는 「결제 중」으로 남은 주문도 셈) | 0건 |

## 2. 시나리오

대기열은 5초마다 종목당 20명을 들여보내요(`queue-service` `queue.schedule`). 들어온 사람이 모두 결제하면 결제도 길게 보면 종목당 초당 4건이에요.
그래서 「종목당 초당 4명이 들어와 입장 확인 → 참가 신청 → 주문 → 결제」를 평소 흐름으로 잡아요.

| 이름 | 내용 | 부하 |
|---|---|---|
| 예열 | 버리는 구간 | 종목 1개, 초당 1명, 1분 |
| S1-1 | 대기열 속도, 종목 1개 | 초당 4명, 2분 |
| S1-5 | 대기열 속도, 종목 5개 | 초당 20명, 2분 |
| S2 | 순간 몰림: 미리 만든 주문 20건을 동시에 결제, 키트 옵션 20개로 나눔 | 20건 × 5번 |
| S3 | 같은 옵션: S2와 같은데 20건 모두 같은 옵션 | 20건 × 5번 |
| S4 | 예치금 지연 0.1 / 0.3 / 0.5초에서 S1-5와 S2 | 지연마다 |
| S5 | 주문 DB 연결 수 20, 예치금 0.3초에서 S1-5와 S2 | 주문만 다시 띄움 |

- S1의 키트 옵션은 앞 5개(티셔츠 사이즈 5개를 흉내) 중 하나를 고르게 골라요. 추천값(미확정).
- 예치금 지연은 주문과 예치금 사이에 Toxiproxy를 두고 넣어요. 예치금 코드는 고치지 않아요. 지연은 요청이 예치금에 닿기 전에 걸려서, 예치금 안 잠금(보관 지갑 줄)은 늘리지 않아요.
- 반복 3회, A와 B는 A, B, A, B, A, B 순서로 번갈아요. 반복마다 DB를 비우고 새로 띄워요.

## 3. 측정 조건

- GitHub Actions `ubuntu-latest`(CPU 4개, 메모리 16GB). 운영(EC2 라지 1대에 서비스, 미디움 1대에 DB)을 비율로만 흉내 내요.

| 컨테이너 | CPU | 메모리 |
|---|---|---|
| 주문 | 1.0 | 1GB |
| 예치금 | 0.5 | 768MB |
| 상품 | 0.5 | 1GB |
| MySQL | 1.0 | 2GB |
| Kafka·Elasticsearch·Redis·Prometheus·Toxiproxy | 나머지 (작게) | |
| k6 | 1.0 | |

(모두 추천값(미확정))

- 주문은 운영 설정(`prod`)에 측정용 환경변수만 더해요: 대기열·회원·크루는 가짜, 예치금·상품은 실제 HTTP, Prometheus 지표 열기.
- 게이트웨이·대기열·회원 서비스는 거치지 않아요. k6가 주문에 `X-Member-Id`를 직접 보내요.

## 5. 한계

- 운영 절대값이 아니라 A·B를 같은 조건에서 비교하는 숫자예요.
- 실행 머신 CPU 4개를 나눠 써서 운영 사양과 다르고, 공용 머신이라 흔들릴 수 있어요. 번갈아 돌려 A·B에 같은 영향을 나눠요.
- 게이트웨이·대기열·회원 서비스를 거치지 않아요. 실제 대기열을 넣은 측정은 같은 스크립트를 모니터링 환경에서 돌릴 수 있게 남겨요.
- 예치금은 결제마다 보관 지갑 한 줄을 잠가서(`CashSupport.lockCustomerAndHoldingWallets`) 예치금 안에서도 결제가 한 줄로 서요. A·B 모두 같아요.
