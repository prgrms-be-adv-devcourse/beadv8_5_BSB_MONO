### 바깥 호출 (2026-11-18 코드로 확인)

예치금이 요청을 처리하는 도중 밖으로 부르는 곳이에요. 이 중 접수가 열릴 때 같이 느려질 법한 셋(토스, Redis, MySQL)을 늦춰요.

| 바깥 | 부르는 요청 | 한 번에 최대로 기다리는 시간 | 이번에 늦추나 |
|---|---|---|---|
| MySQL | 모든 요청 | DB 연결을 얻을 때까지 30초(Hikari 기본값, 연결 10개) | **B-8** |
| Redis | 충전 승인 (충전 이상 감지에서 명령 4번) | 명령마다 2초 | **B-7** |
| 토스 승인 | 충전 승인 | 연결·응답에 5초씩, 결과를 모르면 조회까지 최악 약 19초 | **B-6** |
| 은행 송금 | 정산 지급 | 연결·응답에 5초씩. 운영도 같은 앱 안의 가짜 은행을 HTTP로 불러요 | 아니요 (P8 묶음에서 관찰) |
| 토스 결제취소, 가상계좌 발급, 회원 서비스 | 환급, 회수 청구, 관리자 화면 | | 아니요. 접수 때 드물어요 |

Kafka는 요청 쓰레드에서 보내는 곳이 없어요(알림은 배치 쓰레드). 운영에서 MySQL과 Redis는 모든 서비스가 보조 EC2 한 대를 같이 써요(`k8s/base/app-config.yaml`).

**충전 이상 감지의 Redis 명령 4번 중 2번은 지갑을 잠근 트랜잭션 안에서 불러요**(`ChargeAbuseGuard.registerNewAttempt`).
→ Redis가 느리면 그동안 DB 연결과 회원 지갑 행 락을 함께 쥐어요. 연결은 10개뿐이라, 쓰레드보다 DB 연결이 먼저 찰 거라고 봐요. B-7은 이걸 확인해요.

## 2. 시나리오

### 2-0. 모든 시나리오 공통

1차(`2026-11-16-예치금-부하-판정기준.md` 2-0)와 같은 점:
- k6가 예치금 API를 직접 불러요.
- 반복마다 빈 DB에서 시작하고, 결제 회원 1,000명(지갑마다 1,000만 원)과 판매자 50명으로 시작해요.
- 가짜 PG 결제취소 300ms, 기한 알림 배치 매분 실행이에요.
- 시나리오가 끝날 때마다 돈 확인(C1~C7)을 돌리고 Prometheus 지표를 받아 둬요.

1차와 다른 점:
- **지연 컨테이너(Toxiproxy)**: B-7·B-8 동안만 예치금이 Redis와 MySQL에 갈 때 이 컨테이너를 거쳐요. 그 밖의 시나리오는 1차처럼 바로 가요(7장).
- **PG 승인 지연이나 지연 컨테이너를 바꿀 때 예치금만 다시 띄워요**: 둘 다 띄울 때 정하는 값이에요. B-6 앞(PG 4초), B-7 앞(PG 1초 + 지연 컨테이너 거침), B-1 한계 앞(PG 1초 + 바로)에서 다시 띄워요. DB는 그대로 두고, 다시 띄운 뒤 예열(결제 동시 2개, 30초, 버림)을 다시 돌려요.
- **더 보는 것** (3장): 앱 밖 CPU(cAdvisor), 시나리오별 잠금 대기, DB 연결 받기까지 걸린 시간 등이에요.
  같은 머신에서 자원을 조금 더 써서, 이 점에서도 1차 숫자와 직접 비교하지 않아요.
- **고친 게 없어서 A만 3번 재요.** 1차 A·B 측정의 B(PR #566 끝 커밋)와 같은 예치금 코드예요. 측정한 커밋은 결과 문서에 적어요.

**도는 순서**

```
예열 → B-0 → B-2 → B-0 다시 → B-0 나누기
→ (PG 4초로 다시 띄움, 예열) → B-6
→ (PG 1초 + 지연 컨테이너 거치게 다시 띄움, 예열) → B-7 → B-8
→ (PG 1초 + 바로 가게 다시 띄움, 예열) → B-1 한계
```

한 바퀴 약 60분, 3번 약 3시간이에요(추정).

### B-6·B-7·B-8. 바깥이 느릴 때

세 시나리오는 모양이 같고, 늦추는 대상만 달라요.

- **의심한 곳:** 바깥이 느려지면 충전 승인 하나가 요청 쓰레드(200개)나 DB 연결(10개)을 오래 쥐어요. 그게 다 차면 바깥을 부르지 않는 결제와 잔액 조회도 줄을 서요.
- **늦추는 값**

| 시나리오 | 늦추는 대상 | 값 | 근거 |
|---|---|---|---|
| B-6 | 가짜 PG 승인 | **4초** | 추천값(미확정). 실제 토스 승인은 응답을 5초까지 기다려서, 그 안쪽 값이에요. 가짜 PG는 앱 안에서 잠들어 실제 호출처럼 쓰레드를 쥐어요 |
| B-7 | Redis 명령 | **명령마다 100ms** | 추천값(미확정). 트랜잭션 안의 2번 때문에 충전 하나가 DB 연결을 200ms 넘게 쥐어요. 연결 10개면 초당 약 45건이 한계라, 두 번째 단계(초당 50건)에서 무너지는지 봐요 |
| B-8 | MySQL 쿼리 | **쿼리마다 100ms** | 추천값(미확정). 다른 서비스가 같은 MySQL을 바쁘게 쓰는 상황을 흉내 내요 |

B-7·B-8 동안 가짜 PG 승인은 1초예요(1차와 같아요).

- **요청**
  - 충전 승인: 초당 25 → 50 → 75건, 단계마다 3분이에요. B-6에서 필요한 쓰레드는 100 → 200 → 300개예요.
  - 결제: 동시 4개로 쉬지 않고 보내요(주문 한 대).
  - 잔액 조회(`GET /api/v1/cash/wallets/balance`): 초당 10건이에요.
  - **같은 충전 두 번**: 충전 승인 20건 중 1건(5%)은 첫 요청을 보내고 0.1초 안에 같은 충전 번호로 한 번 더 보내요. 비율은 가정이에요. 실제로 두 번 누르는 비율 자료가 없어요.
- **데이터:** 가입한 지 24시간이 안 된 회원 27,000명이에요(초당 25+50+75건 × 180초). 잔액은 0원이고 한 건에 6만 원이에요.
  - 세 시나리오가 같은 회원을 돌려 써요.
  - 같은 회원은 5분에 3번까지 충전할 수 있는데, 시나리오 사이가 5분보다 길어요.
  - 하루 한도는 100만 원이라 3번(18만 원)은 넘지 않아요.
- **보는 것**
  - 단계별 결제·잔액 조회·충전 p95·p99, 충전 실패율
  - 처리 중인 요청 수, DB 연결 사용 중·대기
  - 두 번째 충전 요청의 응답 시간
- **판정:** X1~X4, C1~C7

### P8 묶음. B-0 → B-2 → B-0 다시 → B-0 나누기

1차 B-0, B-2를 그대로 쓰고 두 구간을 더해요.

1. **B-0**: 1차와 같아요. 환불은 여기 섞인 구간(20초부터)에서 처음 돌아요.
2. **B-2**: 1차와 같아요. 결제 동시 4개 3분, 가운데 1분에 정산 지급 초당 20건이에요. 첫 B-0에서 밀린 요청과 GC가 이 사이에 가라앉아요.
3. **B-0 다시**: B-0의 섞인 구간(결제 후 환불 초당 30건 + 정산 지급 초당 10건, 1분)만 한 번 더 돌려요. 이때는 환불과 정산 지급이 이미 돌아 본 코드예요.
4. **B-0 나누기** (요청 종류 나누기): 「결제 후 환불만 초당 30건」 1분, 「정산 지급만 초당 10건」 1분이에요.

- **보는 것**
  - 구간마다 결제 p95, 그 구간 요청의 p95, 예치금 CPU
  - JFR: 어느 메서드·JIT·GC가 CPU를 쓰는지
  - 가짜 은행 호출 시간과 「송금 결과를 알 수 없습니다」 로그 건수: 예치금이 자기 자신을 HTTP로 부르는 가짜 은행이 쓰레드를 두 배로 쓰는지 봐요. 운영도 같은 구조라, 이게 원인이면 운영 문제예요
- **판정:** P8(1차와 같은 선), R1(원인 고르기)

### B-1 한계 (2초 락 보기)

1차와 같아요. 결제 도착 속도를 초당 20 → 50 → 100 → 200 → 400건으로 2분씩 올려요. 처리량은 판정하지 않고, 락만 L1로 봐요.

## 3. 더 보는 것

새 문제를 찾으려는 게 아니라, **1차 측정에서 답을 막은 빈칸**을 채우려고 더해요. 모두 1차 결과 문서에 적힌 빈칸에서 나왔어요.

「만듦」은 측정 도구에 넣은 거예요. cAdvisor, `sql/14`, `sql/15`, DB 연결 그래프는 11/18에 먼저 넣었어요(`run.sh`, `graph.py`, `compose.load.yml`, `sql/14`, `sql/15`). 처음엔 1차 판정 기준의 고친 기록에 적었다가, 2차 측정에 쓰는 도구라 이 문서로 옮겼어요.

|---|---|---|---|---|
| 앱 밖에서 잰 컨테이너 CPU | B-0 섞인 구간과 B-1 한계 400건 단계에서 앱이 너무 바빠 앱 지표가 비었어요. CPU도 앱 지표로만 봐서 함께 비었어요 (전후 6장 P8, 8장) | cAdvisor(CPU 0.25개)가 컨테이너 CPU·메모리를 1초마다 재고, 그래프 맨 아래에 예치금·MySQL CPU 칸을 붙여요 | 앱이 바빠도 CPU가 상한(0.5개)에 닿았는지 | 만듦 |

| 시나리오별 가장 오래 기다린 락 (L1) | 가장 오래 기다린 락을 회차 끝에 한 번만 읽어서 어느 시나리오인지 몰라요 (전후 7-1, 이 문서 1장) | 시나리오 앞뒤로 `sql/11-lock-stats.sql`을 읽어요(`<시나리오>.lock-before.txt`, `.lock-after.txt`). 최댓값은 0으로 되돌릴 수 없어요(7장) | 어느 시나리오에서 최댓값이 올랐는지. 그 시나리오만의 값은 `sql/15`의 「가장 오래」(잠금을 기다린 SQL이 걸린 시간)로 L1을 봐요 | 만듦 |
| DB 연결 받기까지 걸린 시간 | DB 연결을 기다리는 요청 수만 있어서, 얼마나 기다렸는지 몰라요 | 그래프에 평균과 가장 오래(최근 1~2분의 최댓값)를 더했어요 | 예치금의 연결 대기(최대 30초)가 게이트웨이 제한(10초)을 넘는지. B-7·B-8에서 DB 연결이 먼저 찼는지 | 만듦 |
| JFR | 앱 지표가 빈 구간에 CPU를 누가 썼는지 몰라요 (전후 6장 P8) | 예치금 JVM에 바퀴 내내 켜고, 내릴 때 회차 폴더 `jvm/`에 파일로 남겨요. 다시 띄울 때마다 새 파일이에요 | 어느 메서드·JIT·GC가 CPU를 썼는지. CPU를 1~2% 더 써요 | 만듦 |
| GC 로그 | P8 후보 중 GC(메모리 768MB)를 지우지 못했어요 | 예치금 JVM 옵션, 회차 폴더 `jvm/` | GC가 멈춘 시간 | 만듦 |
| 바쁜 요청 쓰레드 수 | 1차는 쓰레드가 다 차는 상황을 재지 않았어요 | Tomcat 쓰레드 지표(`server.tomcat.mbeanregistry.enabled`) | B-6~B-8에서 쓰레드가 200에 닿았는지. 「처리 중인 요청」과 같은 칸에 그려요 | 만듦 (Spring Boot 4.1에서 `tomcat_threads_busy_threads`가 나오는 것 확인) |

처음 계획한 「MySQL 느린 쿼리 기록」은 넣지 않아요. `sql/15`가 같은 것(어느 SQL이 잠금을 오래 기다렸나)을 시나리오별로 보여 주고, 행 잠금 대기가 들어가는 것도 이미 확인했어요.

`sql/14`는 의논 때 「MySQL CPU를 나눠 쓸까 봐」 빼자고 했던 방법이에요. 1초가 아니라 5초 간격이라 부담이 작고, 「막은 SQL」은 `sql/15`로는 알 수 없어서 넣어요. 잠금 대기가 수천 개 쌓이는 B-1 한계에서는 이 조회가 무거워질 수 있어요(6장).

## 4. 판정 기준

시나리오마다 3회 잰 값의 **중앙값**으로 판정해요. 정확성(C1~C7, 1차 3-3과 같아요)만은 3회 모두 통과해야 해요.

### 4-1. 「문제 있음」 조건 (하나라도 맞으면)

| 번호 | 조건 | 값의 근거 |
|---|---|---|
| X1 | B-6·B-7의 충전 초당 25건 단계에서 결제 p99가 1초 이상, 또는 충전 실패가 1% 이상 | 쓰레드(100개 필요)와 DB 연결이 남는데도 느리면 다른 원인이 있어요. 1초는 1차 P1과 같아요(주문이 기다리는 2초의 절반) |
| X2 | B-6·B-7의 어느 단계든 결제나 잔액 조회 p99가 1초 이상 | 바깥 지연이 바깥을 부르지 않는 API까지 번졌다는 뜻이에요. 몇 번째 단계에서 넘었는지를 문턱으로 적어요 |
| X3 | B-8의 어느 단계든 결제 p95가 2초 이상 | 1차 P8과 같은 선이에요(기획 건강 지표 H7의 경보선) |
| X4 | B-6의 같은 충전 두 번째 요청이 응답까지 걸린 시간의 중앙값이 3.2초(PG 지연 4초의 80%) 이상 | 추천값(미확정). 두 번째 요청이 토스를 다시 부르지 않으면서도 쓰레드를 바깥 지연만큼 쥔다는 근거예요 |
| L1 | B-1 한계가 아닌 시나리오에서 가장 오래 기다린 행 락이 2초 이상 | 주문은 예치금 응답을 2초까지 기다려요(`order.clients.timeout`). B-1 한계(예상 트래픽의 8배)에서만 넘으면 기록만 해요 |
| P8 | B-0에서 결제 p95가 2초 이상 | 1차와 같아요 |

X2·X3에 걸리면 함께 적는 것:
- 처리 중인 요청이 200에 닿은 시각
- DB 연결 대기가 처음 생긴 시각
- 둘 중 먼저인 쪽 → 대안을 고를 때 써요(쓰레드가 먼저면 가상 쓰레드·격벽, DB 연결이 먼저면 트랜잭션 안의 바깥 호출 빼기·연결 수)

### 4-2. P8 원인 고르기 (R1, 판정이 아니라 원인 후보)

| 결과 | 원인 후보 |
|---|---|
| B-0 다시의 결제 p95가 첫 B-0 섞인 구간의 10분의 1 이하 | 처음 도는 경로의 예열이에요. 측정 순서 탓이라 기록만 해요 |
| 그렇지 않음 | B-0 나누기에서 p95가 2초 이상이거나 CPU가 상한(0.5개)에 닿은 구간의 요청 종류, 그리고 JFR에서 CPU를 가장 많이 쓴 곳을 적어요 |

10분의 1은 추천값(미확정)이에요. 1차 B-1·B-2의 결제 p95(29~84ms)가 B-0(약 4초)의 50분의 1쯤이라, 그 사이로 잡았어요.

### 4-3. 이번에 판정하지 않는 것

- 고친 코드가 없어서 「나아짐」(G) 조건은 없어요. 고친 뒤 A·B를 번갈아 잴 때 이 문서의 X·L 조건으로 G를 새로 정해요.
- 1차 G5에서 기준을 넘은 B-1 동시 4개는 이번에 돌리지 않아요. 고친 뒤 A·B를 잴 때 다시 재요.

### 4-4. 이 측정으로 정할 것

| 정할 것 | 시나리오 | 판정·관측 | 결과에 따라 |
|---|---|---|---|

## 5. 측정 조건과 순서

- 1차와 같은 GitHub Actions `ubuntu-latest`(CPU 4개, 메모리 16GB)에서 재요. 컨테이너 자원 제한도 1차와 같아요(예치금 CPU 0.5개·768MB, MySQL 1개·2GB, k6 1개).
- 더한 컨테이너: 지연 컨테이너(Toxiproxy) CPU 0.25개(7장, 처음엔 0.1개), cAdvisor CPU 0.25개예요. 1차 상한 합 약 3.2개에 더해 약 3.7개가 돼요(머신은 4개).
- Actions에서는 PR에 `cash-load-test-2` 라벨을 붙이면 이 순서로 A를 3번 재요.
- 고친 게 없어서 A만 3번 재요.

### 운영 서버에서는 재지 않아요

운영은 메인 EC2 한 대에 앱 12개가 CPU 상한 없이 함께 떠 있고, MySQL·Redis를 모든 서비스가 같이 써요. 부하를 주면 다른 서비스가 함께 느려지고, 매번 조건이 달라서 개선 판정에도 쓸 수 없어요.

대신 운영 지표를 읽어서 이 문서의 가정값을 확인해요. 운영 Prometheus가 이미 모든 Spring 앱의 `/actuator/prometheus`를 모으고 있어요(`k8s/overlays/aws/monitoring/prometheus.yml`).

| 가정값 | 운영에서 볼 지표 |
|---|---|
| 토스 승인 1초 (B-6은 4초) | 토스 승인 호출 시간(`http_client_requests_seconds`, 토스 승인 주소) |
| 토스 결제취소 300ms | 토스 결제취소 호출 시간 |
| 충전 초당 48건 | 충전 승인 요청 수(접수 열린 시간대) |

운영 트래픽이 적어 숫자가 적으면 「표본 적음」으로 적고 가정값을 그대로 둬요.

## 6. 한계

- 1차와 같이 운영 절대값이 아니에요. 공용 머신에서 예치금 CPU 0.5개로 잰 숫자예요.
- B-7·B-8은 지연 컨테이너를 한 단계 더 거쳐요. 지연을 넣지 않은 시나리오와 비교할 때 이 차이가 섞여요.
- B-1 한계는 예치금을 다시 띄우고 예열 30초만 한 뒤 돌아요. 1차는 앞 시나리오를 모두 돈 뒤라 더 데워진 상태였어요.
- cAdvisor와 5초마다 도는 잠금 조회(`sql/14`)가 같은 머신의 자원을 조금 더 써요. 특히 잠금 대기가 수천 개 쌓이는 B-1 한계에서 `sql/14`가 MySQL CPU(1개)를 나눠 쓸 수 있어요.
  → 그래서 이번 숫자는 1차 숫자와 직접 비교하지 않고, 같은 실행 안에서만 비교해요.
- 바깥 지연값(4초, 100ms)과 「같은 충전 두 번」 5%는 가정이에요.
- 실제로는 바깥이 느리면 회원이 기다리다 다시 누르는 일이 늘어요. 이번에는 비율을 고정해서 이 증가는 넣지 않았어요.
- 게이트웨이·주문을 거치지 않아요. 주문이 2초에 포기한 뒤에도 예치금이 계속 일하는 상황은 재현하지 않아요.

## 7. 고친 기록

- 2026-11-19 (측정 도구를 만들면서, 측정 전): 판정 기준 값은 그대로예요. 확인 방법과 도구 자원만 바꿨어요.
  - **가장 오래 기다린 행 락을 시나리오마다 0으로 되돌릴 수 없어요.** MySQL 8.4에서 `SET GLOBAL innodb_monitor_reset`을 `lock_row_lock_time_max`와 `module_lock`에 해 봤지만 값이 그대로였어요(2.4초 대기 뒤 2,440ms, 되돌린 뒤에도 2,440ms).
    그래서 시나리오 앞뒤로 읽어 「이 시나리오에서 최댓값이 올랐나」를 보고, 그 시나리오만의 값은 `sql/15`의 「가장 오래」로 L1을 판정해요. L1의 기준(2초)은 그대로예요.
  - **지연 컨테이너(toxiproxy) CPU를 0.1개에서 0.25개로 올렸어요.** 예치금의 모든 MySQL·Redis 요청이 지나가서, 0.1개면 B-1 한계(초당 400건)에서 이 컨테이너가 병목이 될 수 있어요.
    컨테이너 상한 합은 약 3.7개가 돼요(머신 4개). 그래프의 「앱 밖에서 잰 CPU」 칸에 지연 컨테이너 줄을 넣어, 상한에 닿았는지 봐요.
  - Tomcat 쓰레드 지표는 Spring Boot 4.1에서 `server.tomcat.mbeanregistry.enabled`로 켜지는 것을 확인했어요(`tomcat_threads_busy_threads`, 최대 200).
  - 로컬에서 `QUICK=1`로 한 바퀴 돌려 도구가 동작하는 것만 확인했어요(시나리오 파일, 단계·API별 숫자, 같은 충전 두 번, 지연 넣고 빼기, 예치금 다시 띄우기, JFR·GC 파일, 시나리오별 잠금 기록).
    도중에 맥이 잠들어 시간 숫자는 쓸 수 없어요.
- 2026-11-19 (QUICK을 잠들지 않게 다시 돌린 뒤, 측정 전): 판정 기준 값은 그대로예요. 지연 컨테이너를 거치는 시나리오만 바꿨어요.
  - 한 바퀴가 13분 30초에 끝났어요. 본 측정 한 바퀴는 약 55분으로 봐요.
  - **B-1 한계 초당 400건 근처에서 지연 컨테이너 CPU가 상한(0.25개)에 닿았어요.** 그때 예치금 CPU는 0.36개로 상한(0.5개) 아래였어요.
    → 측정 도구가 결제를 막을 수 있어서, 예치금이 지연 컨테이너를 B-7·B-8 동안만 거치게 바꿨어요. 그 밖의 시나리오는 1차처럼 MySQL·Redis에 바로 가요.
    다시 띄우기가 한 번 늘었어요(B-7 앞에서 거치게, B-1 한계 앞에서 바로 가게).
