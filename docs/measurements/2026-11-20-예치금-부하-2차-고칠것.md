# 예치금 부하 측정 2차: 남은 문제와 고르는 방법 (2026-11-20)

[2차 측정 결과](2026-11-19-예치금-부하-2차.md)에서 남은 문제 다섯 가지를 어떻게 다룰지 정한 기록이에요.
문제마다 지금 코드가 어떻게 생겼는지, 어떤 선택지가 있었는지, 무엇을 왜 골랐는지 적어요.
선택지는 측정 결과를 본 뒤 정했고, 고친 뒤 다시 재서 나아졌는지 봐요(고친 뒤 측정은 아직 안 함).

| | 문제 | 고른 것 | 이번에 코드를 고치나 |
|---|---|---|---|
| ① | 토스가 느리면 결제까지 멈춤 | 충전 확정의 동시 개수 제한 | 고침 |
| ② | Redis가 느리면 DB 연결이 바닥남 | 이상 충전 횟수 세기를 트랜잭션 밖으로 | 고침 |
| ③ | 같은 충전 두 번째 요청이 오래 기다림 | 기다리는 시간 줄이기 (22초 → 3초) | 고침 |
| ④ | 배포 직후 결제가 2초 넘게 멈춤 | 운영 지표로 먼저 확인 → 보이면 보관 지갑을 늦게 잠그기 | 안 고침 (운영 확인 먼저) |
| ⑤ | MySQL이 느리면 예치금이 멈춤 | 기록만 | 안 고침 |

## ① 토스가 느리면 결제까지 멈춤

**측정에서 본 것.** 토스 승인이 4초 걸리면 충전 초당 25건에서 결제 p99가 1.3초가 돼요. 초당 50건부터는 요청 쓰레드 200개가 다 차서 결제가 4~15초로 밀려요(2차 X1·X2).

**지금 코드.** 충전 확정(`CashChargeConfirmUseCase`)은 토스 승인을 DB 트랜잭션 밖에서 불러요. 그래서 DB 연결은 쥐지 않지만, 요청 쓰레드는 토스를 기다리는 동안 계속 잡혀 있어요. 쓰레드는 최대 200개(Tomcat 기본값)를 결제·잔액 조회와 같이 써요.
→ 충전이 쓰레드를 다 가져가면, 토스를 부르지 않는 결제도 쓰레드를 받으려고 줄을 서요.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **가 (고름)** | 충전 확정을 동시에 정해진 수까지만 받고, 넘으면 바로 거절 | 결제 몫 쓰레드가 늘 남아요. 토스를 부르기 전에 거절하니 돈이 빠지지 않아요. 주문이 예치금 결제를 부를 때 쓰는 동시 개수 제한과 같은 방식이에요 | 몰릴 때 충전 거절이 생겨요. 제한 값에 근거가 필요해요 |
| 나 | 가상 쓰레드 켜기 | 쓰레드 200개 상한이 사라져요 | 기다리는 충전이 끝없이 쌓여 병목이 DB 연결 10개로 옮겨 가요. 모든 API의 실행 방식이 바뀌어 다시 재야 해요 |
| 다 | 서킷 브레이커 | 토스 장애 동안 쓰레드를 아예 쓰지 않아요 | 라이브러리가 늘고, 「느린 성공(4초)」을 어디서부터 장애로 볼지 정해야 해요 |
| 라 | 토스 시간 제한 줄이기 (지금 연결·응답 각 5초) | 설정만 바꿔요 | 4초 지연에는 효과가 없어요. 「승인됐는지 모름」이 늘어 재확인 배치 부담이 커져요 |

**고른 이유.** 결제를 지키는 게 목적이고, 가는 돈 처리 순서를 건드리지 않아요. 팀에서 이미 쓰는 방식이라 읽기도 쉬워요.

**정한 값.** 동시 100개(`cash.charge.confirm.max-concurrent`).
- 쓰레드 200개의 절반이에요. 나머지 절반은 결제·잔액 조회 몫으로 남겨요.
- 예상 트래픽(충전 초당 48건) × 평소 승인 시간(약 1초, 1차 B-5에서 가짜 PG 1초로 p95 1.3초) ≈ 48개의 두 배라, 평소에는 거절이 나지 않아요.
- 토스가 4초로 느려지면 초당 25건까지 받아요(25 × 4 = 100). 그 위는 거절해요.
- 100은 이 계산으로 정한 추천값(미확정)이에요. 고친 뒤 B-6을 다시 재서 결제가 지켜지는지 봐요.

**코드를 보고 바꾼 것: 503이 아니라 429로 답해요.**
프론트(`use-confirm-charge-return.ts`)는 충전 확정이 409나 5xx로 끝나면 「서버가 처리했는지 모름」으로 보고 기다리라고만 안내해요. 다시 결제하면 카드에서 두 번 빠질 수 있어서예요.
그런데 이 거절은 토스를 부르기 전이라 돈이 빠지지 않은 게 확실해요. 503으로 답하면 사용자는 오지 않을 결과를 기다려요.
→ 그 밖의 4xx는 프론트가 「돈이 빠지지 않은 실패」로 보고 다시 결제하게 해요. 그래서 쿨다운과 같은 429(`요청이 너무 많음`)로 답해요. 프론트는 고치지 않아요.

## ② Redis가 느리면 DB 연결이 바닥남

**측정에서 본 것.** Redis가 명령마다 100ms 느리면 충전 초당 25건에서 DB 연결 10개가 다 차요. 쓰레드는 50~80개라 남아 있어요(2차 B-7).

**지금 코드.** 새 충전을 등록하는 트랜잭션(`claimChargeLocked`) 안에서, 회원 지갑을 잠근 채 이상 충전 횟수를 Redis에 올려요(`ChargeAbuseGuard.registerNewAttempt`, Redis 명령 2번).
→ Redis가 느린 만큼 DB 연결과 회원 지갑 잠금을 오래 쥐어요.
Redis가 아예 실패하면 감지를 건너뛰는 것(fail-open)은 이미 돼 있어요. 명령 시간 제한도 2초로 걸려 있어요.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **가 (고름)** | 횟수 세기를 등록 트랜잭션이 끝난 뒤로 옮기기 | DB 연결·지갑 잠금을 쥔 시간이 Redis 속도와 상관없어져요 | 쿨다운에 걸렸을 때 이미 저장된 등록을 되돌리는 단계가 하나 더 필요해요(아래) |
| 나 | Redis 시간 제한을 짧게 하고, 넘으면 감지를 건너뛰기 | 설정만 바꿔요 | 그동안 이상 충전 감지가 꺼져요. 보안 정책으로 정할 일이에요. 짧은 지연(100ms)에는 효과가 없어요 |

**고른 이유.** 원인(잠금을 쥔 채 바깥을 부름)을 없애는 방법이에요. 나는 감지를 끄는 정책 판단이 들어가요.

**코드를 보고 더한 것: 쿨다운에 걸리면 등록을 실패로 돌려요.**
지금은 횟수 세기가 쿨다운 예외를 던지면 등록 트랜잭션이 통째로 롤백돼, 충전 행이 「처리 중」으로 남지 않아요.
트랜잭션 밖으로 옮기면 그 롤백이 없어요. 그래서 쿨다운에 걸리면 같은 충전을 「실패」로 바꾸는 트랜잭션을 한 번 더 돌리고 쿨다운 예외를 그대로 던져요.
- 토스는 부르지 않았으니 돈은 빠지지 않아요. 사용자에게는 지금처럼 쿨다운 안내(429)가 가요.
- 달라지는 점 1: 쿨다운에 걸린 새 충전이 「실패」 행으로 남아요. 지금은 행이 아예 없어요. 같은 주문번호로 다시 확정하면 실패 건 재시도로 처리돼요(지금 코드에 이미 있는 길).
- 달라지는 점 2: 일일 한도·보유 한도에 걸려 거절된 시도는 더는 횟수에 들어가지 않아요. 지금은 한도 확인 전에 세서 들어가요. 이 시도들은 토스를 부르지 않고 거절되므로 쿨다운으로 막을 이유가 작아요.
- 「실패」로 바꾸는 트랜잭션마저 실패하면 행이 「처리 중」으로 남아요. 이때는 지금도 있는 재확인 배치가 2분 뒤 토스에 다시 물어 정리해요.

## ③ 같은 충전 두 번째 요청이 오래 기다림

**측정에서 본 것.** 토스가 4초 걸릴 때, 같은 주문번호로 두 번째 확정 요청이 오면 응답까지 중앙값 8.7초가 걸려요(2차 X4). 그동안 요청 쓰레드를 쥐어요.

**지금 코드.** 두 번째 요청은 0.1초마다 결과를 다시 조회하며 최대 220번(22초) 기다려요. 그래도 안 끝나면 「이미 처리 중인 충전 요청입니다」(409)로 답해요.
22초는 첫 요청이 걸릴 수 있는 가장 긴 시간(19초)보다 길게 잡은 값이에요. 두 번째 요청도 결과를 받게 하려는 뜻이었어요.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| 가 | 기다리지 않고 바로 409 | 쓰레드를 바로 돌려줘요 | 첫 요청이 몇십 ms면 끝나는 평소에도 두 번째 요청이 결과 대신 409를 받아요 |
| **나 (고름)** | 기다리는 시간만 줄이기 (22초 → 3초, 0.1초 × 30번) | 평소(승인 1초 안팎)에는 그대로 결과를 받아요. 토스가 느릴 때만 3초 뒤 409로 끝나요 | 토스가 느릴 때 두 번째 요청이 쓰레드를 3초는 쥐어요 |
| 다 | 그대로 두고 ①의 동시 개수 제한에 맡기기 | 바꿀 게 없어요 | 두 번째 요청이 제한 몫을 22초씩 차지해요 |

**고른 이유.** 평소 동작은 그대로 두고, 느릴 때만 빨리 끝내요.

**프론트 확인.** 프론트는 409를 「결과를 모름, 기다리세요」로 보여 주고, 같은 충전 확정을 다시 부르지 않아요. 첫 요청이 끝나면 잔액에 들어가요.
→ 두 번째 요청이 3초 뒤 409를 받아도 돈은 맞아요. 또 프론트는 한 충전에 확정을 한 번만 보내서(보내기 전에 기록), 두 번째 요청은 원래 드물어요.

## ④ 배포 직후 결제가 2초 넘게 멈춤

**측정에서 본 것.** 막 띄운 직후 예열(사용자 2명)에서 보관 지갑 락을 최대 2.6초 기다렸어요(2차 L1).
JFR로 보니, 락을 쥔 결제가 그동안 클래스를 처음 읽고 JIT 컴파일을 하고 있었어요. 예치금은 CPU 상한(0.5개)에 닿아 있었어요(2차 5장).

**지금 코드.** 결제는 지갑을 ID 순서대로 잠가요. 보관 지갑이 2번이라 가장 먼저 잠기고, 커밋까지 쥐어요.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **가 (먼저 함)** | 운영 지표로 배포 직후 결제가 느려지는지 확인 | 운영은 CPU 상한이 없어(요청 50m, 상한 없음) 측정보다 덜할 수 있어요. 고칠지 근거가 생겨요 | 고치는 건 아니에요 |
| **나 (보이면 함)** | 보관 지갑을 마지막에(커밋 직전에) 잠그기 | 첫 실행 비용이 잠금 전에 지나가요. 평소 잠금 시간도 짧아져 초당 400건 한계에도 도움돼요 | 결제·환불·정산의 잠금 순서를 모두 바꿔요. 교착 상태 검토와 돈 테스트가 많이 필요해요 |
| 다 | 요청을 받기 전에 결제 경로를 미리 돌리고 나서 「준비됨」 | 잠금 순서를 안 바꿔요 | 운영에서 쓸 예열용 요청과 데이터를 설계해야 해요 |
| 라 | 락 대기 시간 제한 + 503 | 주문이 2초에 포기하기 전에 깔끔한 실패를 받아요 | 원인은 그대로예요. 실패가 늘 수 있어요 |

**고른 이유.** 측정 환경의 CPU 상한이 원인의 일부라, 운영에서도 생기는지 먼저 봐요. 생기면 나를 해요. 나는 주문 담당(다윗님)께 여쭌 「보관 지갑을 마지막에 잠그기」와 같은 이야기라 그 답과 같이 정해요.

## ⑤ MySQL이 느리면 예치금이 멈춤

**측정에서 본 것.** 쿼리마다 100ms 느리면 모든 요청이 60초 제한에 걸리고, 충전이 72~100% 실패해요(2차 X3).

**지금 코드.** DB 연결 10개, 연결을 기다리는 시간 제한은 기본값 30초예요.

| | 방법 | 장점 | 단점 |
|---|---|---|---|
| **가 (고름)** | 그대로 두고 기록만 | MySQL 장애는 예치금 혼자 막을 수 없어요 | 장애 때 요청이 오래 매달려요 |
| 나 | 연결 대기 시간 줄이기 (30초 → 예: 2초) | 빨리 실패하고 쓰레드가 빨리 돌아와요 | 잠깐 몰릴 때도 실패가 생길 수 있어요 |
| 다 | 연결 수 늘리기 (10 → 20) | 연결이 모자라는 시간이 줄어요 | MySQL이 느린 게 원인이라 오히려 더 느려질 수 있어요. 운영 MySQL은 서비스 12개가 같이 써요 |

**고른 이유.** 예치금 코드로 풀 문제가 아니에요. ①을 고친 뒤 다시 재서 나를 할지 정해요.

## 고친 뒤 측정: 판정 기준 (측정 전에 정함)

①②③을 고친 코드(B)와 고치기 전 코드(A)를 같은 머신에서 번갈아 3번씩 재요. 숫자를 보고 기준을 바꾸지 않아요.

- **A**: B에서 ①②③ 커밋 하나(`perf(cash): 바깥이 느릴 때 …`)만 되돌린 코드 (`container/ab-fixes.txt`)
- **시나리오**: 예열 → (토스 4초로 다시 띄움) B-6 → (지연 컨테이너를 거쳐 다시 띄움) B-7. 단계·부하는 2차와 같아요
- **실행**: PR에 `cash-load-test-2ab` 라벨. 한 바퀴 약 30분, A·B 3번씩이면 약 3시간

| 번호 | 무엇 | B가 이러면 「나아짐」 | 근거 |
|---|---|---|---|
| G1 | ① B-6 충전 초당 50건·75건 단계의 결제 p99 | 1초 미만 | 2차 X2와 같은 선. 2차는 4.4~15초 |
| G2 | ① B-6 모든 단계의 잔액 조회 p99 | 1초 미만 | 2차 X2와 같은 선. 2차는 2.5~15초 |
| G3 | ③ B-6 같은 충전 두 번째 요청의 응답 중앙값 | 3.2초 미만 | 2차 X4와 같은 선. 2차는 8.7초 |
| G4 | ② B-7 충전 초당 25건 단계의 결제 p99 | 1초 미만 | 2차 X1과 같은 선. 2차는 4.4초 |
| G5 | 돈 확인 C1~C7 | A·B 모든 회차에서 어긋남 0 | 1·2차와 같아요 |

- 값은 3회 중앙값으로 판정해요. 모두 맞으면 「나아짐」, 하나라도 못 미치면 그 항목만 「나아지지 않음」으로 적어요.
- A가 2차와 비슷하게 기준을 넘는지도 봐요. A가 넘지 않으면 그 회차의 머신이 2차와 달랐다는 뜻이라, B만으로 나아졌다고 말하지 않아요.
- **판정하지 않고 적는 것**: 단계별 충전 거절(429) 비율과 실제로 끝난 충전 수(①의 대가), 쓰레드·DB 연결 그래프, 같은 충전 두 번째 요청 중 409로 끝난 비율(③의 대가)
