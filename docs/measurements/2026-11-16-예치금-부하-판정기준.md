# 예치금(cash) 부하 측정: 판정 기준과 시나리오 (2026-11-16)

예치금을 자원을 묶은 컨테이너에서 다시 재요. 지금 코드를 A, 고친 코드를 B라고 불러요.
맥에서 잰 측정(`2026-11-16-예치금-부하.md`)은 연습이에요. 다른 프로젝트 컨테이너가 함께 떠 있었고 자원도 묶지 않아서, 판정에는 쓰지 않아요.

이 문서는 **측정 전에** 커밋해요. 숫자를 본 뒤 기준을 결과에 맞춰 바꾸지 않게 하려는 거예요. 바꿔야 하면 지우지 않고 「6. 고친 기록」에 이유와 함께 남겨요.
근거 없이 고른 값에는 「추천값(미확정)」을, 자료가 없어 우리가 정한 값에는 「가정」을 붙였어요.

## 1. 예상 트래픽

### 1-1. 우리가 정한 값

| 값 | 정한 값 | 근거 |
|---|---|---|
| 동시에 접수를 여는 종목 | **12개** (대회 3개 × 종목 4개). 가정 | 국내 대회는 연 약 450개, 대회당 평균 3,560명이에요(`docs/ideation/11-market-sizing.md`). 일주일에 9개꼴이라 성수기에 접수 시작이 겹치는 대회를 3개로 봤어요. 종목은 5K·10K·하프·풀 4개예요 |
| 운영 서버 | **예치금 1대, 주문 1대**. 주문 2대일 때도 한 번 더 재요 | k8s 설정이 둘 다 `replicas: 1`이에요. 주문 설정 주석에 2대 경우가 적혀 있어요 |
| 충전하는 사람 | **참가자 100%**. 가정 | 처음 쓰는 사람은 예치금이 0원이라, 결제하기 전에 반드시 충전해요 |

### 1-2. 예치금이 받는 부하

**결제.** 대기열은 5초마다 종목당 20명을 들여보내요(`queue.schedule`). 그래서 들어오는 속도는 종목당 초당 4명이에요.
- 종목 12개면 초당 48명이에요. 들어온 사람이 모두 결제하면 결제도 **초당 48건**이에요.
- 주문은 예치금 결제를 **주문 서버 한 대당 동시에 4개까지만** 보내요. 1초 안에 자리가 나지 않으면 「잠시 후 다시」로 돌려보내요(`max-concurrent-pay: 4`, `pay-acquire-timeout: 1s`).
- → 예치금에는 결제가 한꺼번에 몰려오지 않아요. 동시 4개(주문 2대면 8개)가 쉬지 않고 들어오는 모양이에요.
- → 이 모양에서 초당 48건을 넘게 처리하려면 결제 한 건이 약 83ms(4 ÷ 48) 안에 끝나야 해요.

**충전.** 모자란 예치금은 입장한 뒤 결제 화면에서 바로 충전해요(`frontend/src/views/checkout/ui/CheckoutPage.tsx`). 대기열 화면에는 충전으로 가는 길이 없어요.
- → 충전 속도도 들어오는 속도를 넘지 못해요. 모두 충전한다고 보면 **초당 48건**이에요.
- 다만 게이트웨이와 예치금은 충전할 때 대기열을 확인하지 않아요. 기다리는 동안 다른 탭에서 충전하는 길이 있어요. 몇 명이 그렇게 할지는 몰라요. 그래서 한계를 보는 측정(1,000명 동시)으로만 따로 둬요.
- 가짜 PG 승인에는 **1초 지연**을 넣어요. 실제 토스 승인 시간은 아직 재지 않아서 추천값(미확정)이에요.

**15분 동안 쌓인 사람.** 입장은 15분 동안 유지돼서 한 종목에 최대 3,600명이 들어와 있을 수 있어요.
하지만 사람마다 들어온 시각이 달라서, 결제와 충전이 한 순간에 맞춰 몰리지 않아요. 결제는 주문이 동시 4개로 묶고, 충전 몰림은 B-5 한계 측정으로 봐요.

## 2. 시나리오

### 2-0. 모든 시나리오 공통

- **부르는 곳:** k6가 예치금 API를 직접 불러요. 게이트웨이·주문은 거치지 않아요. 주문의 「동시 4개」는 k6의 동시 사용자 수로 흉내 내요.
- **데이터:** 반복마다 빈 DB에서 시작해요. 시드는 연습과 같아요.
  - 결제 회원 1,000명. 지갑마다 1,000만 원(잔액 상한)을 넣어 잔액 부족이 나지 않게 해요.
  - 판매자 50명
  - 주문·정산 번호는 실행마다 겹치지 않게 매겨요.
- **결제 한 건:** `POST /internal/v1/cash/payments/{주문 번호}`. 1,000명 중 무작위 회원이 1만 원을 내요.
- **예치금 설정:** 측정용 설정 세 가지를 켠 채 한 번만 띄워요.
  - 가짜 PG 결제취소 300ms
  - 가짜 PG 승인 1초
  - 기한 알림 배치를 매분 실행

  결제·정산 지급은 PG를 부르지 않아서 이 설정의 영향을 받지 않아요. 기한 알림 대상은 B-4 직전에만 넣어서, 다른 시나리오 동안에는 배치가 대상 0명으로 금방 끝나요.
- **도는 순서:** 예열(결제 동시 2개, 30초, 버림) → B-0 → B-1 → B-2 → B-3 → B-4 → B-5 → B-5 한계. B-1 한계는 첫 A에서만 한 번 돌려요.
- **끝날 때마다:** 시나리오가 끝나면 정확성 확인(3-3)을 돌려요. 그리고 그 시나리오 시간의 Prometheus 지표를 파일로 받아 둬요.

### B-0. 동시에 몰려도 돈이 한 번만 움직이는지

- **의심한 곳:** 같은 요청이 겹치면 결제, 정산 지급, 충전이 두 번 처리될 수 있어요. 응답이 모두 200이어도 돈은 두 번 빠졌을 수 있어요. 그래서 판정은 DB로 해요.
- **요청**
  1. 같은 주문 결제 100번 동시
  2. 같은 정산 지급 50번 동시. 정산 서비스는 200(이미 지급됨)이나 503(결과 모름, 다시 보냄)을 받아야 해요. 500은 받으면 안 돼요.
  3. 같은 충전 승인 50번 동시(같은 충전 번호). PG 승인은 한 번만 불려야 해요.
  4. 1분 동안 결제 직후 환불(초당 30건)과 정산 지급(초당 10건)을 섞기
- **보는 지표:** 응답 코드별 건수, 정확성 C1~C7, PG 승인 호출 수
- **판정:** P4, C1~C7

### B-1. 주문이 보내는 모양 그대로 결제를 받을 때

- **의심한 곳:** 결제마다 회원 지갑 행과 주문 대금을 맡아 두는 지갑 행을 잠가요(`CashSupport.lockCustomerAndHoldingWallets`). 맡아 두는 지갑은 하나뿐이라 모든 결제가 이 한 행에서 줄을 서요.
  연습에서는 초당 약 190건에서 막혔어요.
- **요청:** 결제를 동시 4개(주문 1대)로 2분, 이어서 동시 8개(주문 2대)로 2분 불러요. 응답을 받자마자 다음 결제를 보내요.
- **왜 이 모양인가:** 주문 서버 한 대는 예치금 결제를 동시에 4개까지만 보내요(1-2). 그래서 예치금이 받는 결제는 「초당 몇 건」이 아니라 「동시 몇 개」로 정해져요.
- **보는 지표**
  - 처리량(초당 결제 수). 1장에서 계산한 필요량은 초당 48건이에요.
  - 결제 p50·p95·p99
  - DB 연결 사용 중·대기
  - MySQL 행 락 대기
- **판정:** P1(동시 4개), P2(동시 8개), P8

### B-1 한계. 결제 도착 속도를 올리면 어디서 막히나 (판정 안 함)

- 연습과 같은 방식이에요. 결제 도착 속도를 초당 20 → 50 → 100 → 200 → 400건으로 2분씩 올려요.
- 주문이 동시 수를 묶어 주지 않는 경우라 실제 모양과 달라요. 그래서 판정에는 쓰지 않아요.
- 막히는 속도를 기록해, 초당 48건의 몇 배까지 여유가 있는지 적어요. 첫 A에서만 돌려요.

### B-2. 결제 중에 정산 지급이 몰릴 때

- **의심한 곳:** 정산 지급도 결제와 같은 「맡아 두는 지갑」 행을 잠가요. 정산 배치는 운영에서 새벽 4시에 몰려 와요.
  그 시각에 접수가 열려 있으면 결제가 정산 뒤에 줄을 설 수 있어요.
- **요청:** 결제를 동시 4개로 3분 동안 쉬지 않고 불러요. 가운데 1분에만 정산 지급을 초당 20건 섞어요. 정산 지급은 가짜 은행 송금을 불러요.
- **값:** 정산 지급 초당 20건은 추천값(미확정)이에요. 정산 배치가 판매자 몇 명에게 한꺼번에 보내는지 아직 재지 않았어요.
- **보는 지표**
  - 앞 1분 · 가운데 1분 · 뒤 1분의 결제 처리량과 p95·p99
  - 정산 지급 p95
  - 은행 호출 평균 시간
  - 행 락 대기
- **판정:** P3, P8

### B-3. 카드 장수가 많은 회원이 전액 환급할 때

- **의심한 곳:** 환급(`CashWithdrawalUseCase`)은 카드 결제취소를 한 장씩 차례로 불러요. 응답 시간이 「장수 × PG 결제취소 시간」이 돼요.
- **데이터:** 카드 충전이 1장·3장·5장인 회원을 30명씩 만들어요. 한 장에 1만 원이고 잔액은 충전한 만큼이에요.
- **요청:** 장수마다 회원 30명이 `POST /api/v1/cash/withdrawals`로 전액 환급해요. 동시에 10명씩이에요. 카드로 다 돌려줄 수 있어서 계좌 정보는 보내지 않아요.
- **값:** PG 결제취소 300ms와 동시 10명은 추천값(미확정)이에요. 실제 토스 결제취소 시간은 아직 재지 않았어요.
- **보는 지표:** 장수별 p95, 실패율
- **판정:** P5

### B-4. 카드 취소 기한 알림 배치

- **의심한 곳:** 배치가 대상 회원마다 지갑과 충전 내역을 다시 조회해요. 연습에서 SQL 수가 「대상 × 2 + 4」였어요.
- **데이터:** 카드 결제취소 마지막 날이 정확히 3일 뒤인 충전 1건(1만 원)을 가진 회원을 100명 · 1,000명 · 10,000명 만들어요.
- **요청:** 배치가 한 번 돌 때까지 기다려요. 회원마다 알림이 Kafka로 나가요.
- **보는 지표**
  - 걸린 시간: Spring이 배치 실행마다 남기는 시간이에요. 알림 전송까지 포함해요.
  - SQL 수와 DB 시간: 배치 한 번 동안 쌓인 예치금 표 문장이에요.
- **판정:** P6. 연습에서 걸린 시간의 약 90%가 DB 밖이었어서, 고칠 때는 시간이 어디에 쓰이는지 추적을 함께 봐요.

### B-5. 접수가 열렸을 때 충전 승인

- **의심한 곳:** 충전 승인은 게이트웨이에서 예치금으로 바로 가요. 결제와 달리 주문의 동시 호출 제한을 거치지 않아요.
  승인 하나는 세 단계로 지나가요.
  1. 회원 지갑을 잠그고 충전을 선점해요(트랜잭션 ①).
  2. PG 승인을 기다려요(트랜잭션 밖).
  3. 지갑에 반영해요(트랜잭션 ②).

  코드로 보면 PG를 기다리는 동안 트랜잭션은 닫혀 있어요(`CashChargeConfirmUseCase`, `open-in-view: false`). 그래서 막힌다면 DB 연결보다 요청을 처리하는 스레드(200개)가 먼저 찰 거라고 봐요.
- **데이터:** 가입한 지 24시간이 안 된 회원 30,000명을 만들어요. 잔액은 0원이에요.
  - 가입 직후 회원은 「신규 회원 고액 충전 표시」 확인 조회가 한 번 더 나가요. 처음 쓰는 사람이 대부분이라 이쪽을 골랐어요.
  - 회원 한 명은 한 번만 충전해요. 같은 회원은 5분에 3번까지만 충전을 시도할 수 있어서(`MAX_CHARGE_ATTEMPTS_PER_WINDOW`), 같은 회원을 다시 쓰면 제한에 막혀요.
- **요청:** 초당 48건으로 10분 동안 `POST /api/v1/cash/charges/confirm`을 불러요. 한 건에 6만 원이고, 충전 번호는 모두 달라요.
- **값:** 6만 원은 기획의 평균 참가비예요(`docs/ideation/11-market-sizing.md` A3). PG 승인 1초는 추천값(미확정)이에요.
- **보는 지표**
  - 충전 p50·p95·p99와 실패율
  - 처리 중인 요청 수(스레드)
  - DB 연결 사용 중·대기
  - 정확성 C6
- **판정:** P7, P8, C6

### B-5 한계. 대기열을 거치지 않고 1,000명이 동시에 충전 (돈만 판정)

- 앱이 안내하는 길은 아니지만, 기다리는 동안 다른 탭에서 충전할 수 있어요. 그래서 대기열이 막아 주지 않는 몰림을 따로 봐요.
- **요청:** B-5에서 쓰지 않은 회원 1,000명이 같은 순간에 한 번씩 충전 승인을 불러요.
- **보는 지표:** 마지막 응답까지 걸린 시간, p95·p99, 실패 건수, 처리 중인 요청 수 최대, DB 연결 대기 최대
- **판정:** C1~C7만 봐요. 응답 시간은 기록만 해요. 스레드 200개를 넘는 몰림이라 느려지는 것은 예상하고 있어요. 이 측정에서는 돈이 맞는지를 봐요.

## 3. 판정 기준

시나리오마다 3회 잰 값의 **중앙값**으로 판정해요. 정확성(C)만은 3회 모두 통과해야 해요.

### 3-1. A를 「문제 있음」으로 보는 조건 (하나라도 맞으면)

| 번호 | 조건 | 값의 근거 |
|---|---|---|
| P1 | B-1 동시 4개에서 처리량이 초당 48건 밑, 또는 결제 p99가 1초 이상 | 48건은 1장 예상 트래픽이에요. 1초는 주문이 예치금 응답을 2초까지 기다리니(`order.clients.timeout`) 그 절반이에요 |
| P2 | B-1 동시 8개에서 P1과 같은 조건 | 주문 2대일 때예요 |
| P3 | B-2 정산이 섞인 1분 동안 결제 p99가 1초 이상, 또는 처리량이 앞 1분의 80% 밑 | 1초는 P1과 같아요. 80%는 추천값(미확정) |
| P4 | B-0 같은 정산 동시 지급에서 서버 오류(500)가 1건 이상 | 정산 서비스는 「이미 지급됨」을 받아야 다시 부르지 않아요. 서버 오류를 받으면 실패로 보고 다시 불러요 |
| P5 | B-3 카드 5장 환급 p95가 1초 이상 | 추천값(미확정). 화면에서 기다리는 요청이에요 |
| P6 | B-4 대상이 100명에서 10,000명이 될 때 SQL 수가 10배 넘게 늘어남 | 추천값(미확정). 대상 수에 비례하는지를 봐요 |
| P7 | B-5 충전 p95가 2초 이상(PG 1초 + 1초), 또는 실패가 1% 이상 | 둘 다 추천값(미확정) |
| P8 | 어느 시나리오든 결제 p95가 2초 이상 | 기획 건강 지표 H7의 경보선이에요(`docs/ideation/07-north-star-metrics.md`) |

P1·P2가 맞지 않으면 「결제는 예상 트래픽에서 버틴다」고 그대로 적고 결제 잠금은 고치지 않아요. 이때 B-1 한계에서 막힌 속도가 초당 48건의 몇 배인지를 여유로 적어요.

### 3-3. 정확성 확인 (A·B 모두, 실행마다 끝에 SQL로)

  1. **A를 3번** 재요. P1~P8로 무엇을 고칠지 정해요.

- 실행마다 DB를 비우고 컨테이너를 새로 띄워요.

## 5. 한계

- 운영 절대값이 아니라, 같은 조건에서 A와 B를 비교하는 숫자예요.
