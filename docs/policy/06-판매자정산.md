### 2차 회수금 입금 (가상계좌)

> 2026-11-10 결제 담당(김소희)이 정산 쪽 구현(BUK-88)에 맞춰 정한 내용이에요 (BUK-84).

**무엇을 하나**

- 판매자가 돌려줄 돈(청구)마다 토스 가상계좌를 하나 발급해요. 판매자가 그 계좌로 입금하면 결제가 홀딩 지갑에 기록하고, 정산이 회수를 끝내요.
  → 관리자가 통장을 보고 입금을 맞추지 않아도 되고, 1차 정산 뒤 환불로 모자랐던 홀딩 지갑이 채워져요.
- 실제 돈을 따로 보관하는 신탁계좌는 만들지 않아요. 회수금도 충전금처럼 예치금 보관 통장 한 곳에 모였다고 보고 장부로만 관리해요.
  실서비스라면 선불충전금 별도관리가 필요하지만 프로젝트 범위 밖이에요.

**흐름과 담당**

| 순서 | 하는 일 | 담당 |
|---|---|---|
| 1 | 청구를 만들면 결제에 그 청구의 가상계좌 발급을 요청해요 (청구 ID, 금액) | 정산 |
| 2 | 토스에서 가상계좌를 발급받아 은행과 계좌번호를 돌려줘요 | 결제 |
| 3 | 판매자에게 그 계좌로 입금하라고 알려요 | 정산 |
| 4 | 판매자가 입금해요 (테스트에서는 토스 개발자센터의 「입금처리」 버튼) | - |
| 5 | 토스가 보낸 입금 알림을 받아요 | 결제 |
| 6 | 입금을 확인하고 홀딩 지갑에 장부를 남겨요 | 결제 |
| 7 | 정산에 입금 메시지를 보내요 → 정산이 받아 회수를 끝내요 | 결제(보내기), 정산(받기) |

- 발급(1~2)은 요청하고 바로 응답받는 API예요. 정산이 계좌번호를 받아야 판매자에게 알릴 수 있어서예요.
- 입금 알림(7)은 Kafka 메시지예요. 결제는 입금됐다는 사실만 알리고, 받는 쪽이 처리하기를 기다리지 않아요.

**가상계좌**

- 청구 하나에 계좌 하나예요. 청구 ID를 토스 주문번호로 써요.
- 같은 청구로 다시 요청하면 새로 만들지 않고 이미 발급한 계좌를 돌려줘요.
  → 정산이 응답을 받지 못해 다음 날 다시 요청해도, 판매자에게 알린 계좌가 바뀌지 않아요.
- 토스에 발급을 요청하기 전에 그 주문번호로 만든 계좌가 있는지 먼저 조회하고, 있으면 그 계좌를 써요.
  → 발급 직후 결제 서버가 죽어 계좌를 저장하지 못했어도, 다시 요청할 때 계좌가 둘로 늘지 않아요.
- 은행은 국민은행 한 곳으로 정해요. 판매자가 은행을 고르지 않아요.
- 유효기간은 발급일부터 90일(토스 최대)이에요. 정산의 입금 기한(청구 30일)을 넘겨 늦게 입금해도 자동으로 기록돼요.
- 다시 발급하지 않아요. 90일이 지나면 계좌가 닫히고, 관리자가 판매자와 직접 맞춰요.

**입금 확인**

- 토스의 입금 알림을 받으면 아래 세 가지가 모두 맞아야 장부를 남겨요.
  1. 알림에 담긴 비밀값이 발급 때 받아 둔 값과 같다 → 다른 곳에서 꾸며 보낸 알림을 걸러요.
  2. 토스에 다시 조회했을 때 입금 완료다.
  3. 입금 금액이 청구 금액과 같다.
- 모르는 주문번호의 알림에도 정상으로 응답해요. → 토스가 같은 알림을 계속 다시 보내지 않아요.
- 알림이 오지 않을 때를 대비해 스케줄러가 입금 대기 중인 계좌를 토스에 주기적으로 다시 조회해요. 입금됐으면 알림을 받은 것과 똑같이 처리해요.
- 다시 조회하다 한 건에서 오류가 나면 그 건은 입금 대기로 두고 오류 기록을 남긴 뒤 다음 건을 봐요. 다음 실행(10분 뒤)에 다시 봐요(BUK-104).
  → 한 건 때문에 뒤의 입금이 기록되지 않는 일이 없어요.
- 다른 금액의 입금은 은행과 토스가 이체 단계에서 막아요. 그래도 금액이 다르면 장부도 메시지도 남기지 않고 오류 기록만 남겨요.

**장부**

- 입금이 확인되면 홀딩 지갑에 들어온 금액만큼 한 줄(+)을 남겨요. 충전처럼 돈이 플랫폼 밖에서 들어오므로 다른 지갑의 짝 줄은 없어요.
- 청구 하나에 한 번만 남겨요. 같은 알림이 여러 번 오거나, 알림과 스케줄러가 동시에 처리해도 두 번 기록되지 않아요.

**정산에 알리기**

- 토픽은 `queuing.claim.deposited`, 키는 청구 ID, 내용은 청구 ID·입금 금액·입금 시각이에요.
- 장부를 남기는 같은 트랜잭션에서 회수 입금 기록을 「입금 완료, 아직 안 보냄」으로 저장해요. 스케줄러가 안 보낸 기록을 찾아 보내고,
  Kafka가 받았다고 답하면 보낸 시각을 채워요. → 장부는 남았는데 메시지만 빠지는 일이 없어요.
  아웃박스 방식이에요. 보낼 메시지가 한 종류이고 내용이 회수 입금 기록에 다 있어서, 아웃박스 전용 테이블 대신 회수 입금 기록을 함께 써요.
- 같은 메시지가 두 번 갈 수 있어요. 정산은 이미 끝낸 청구면 건너뛰어요.
- 다시 조회하는 단계가 오류로 끝나도 같은 실행에서 정산 알림은 보내요(BUK-104).
  → 이미 입금 완료로 기록한 건의 회수가 멈추지 않아요.

**사람이 맞추는 경우**

- 입금 금액이 청구 금액과 다르다: 결제는 기록하지 않아요. 오류 기록을 보고 관리자가 맞춰요.
- 90일 안에 입금하지 않았다: 계좌가 닫혀요. 관리자가 판매자와 맞추고 관리자 입금 확인으로 끝내요.
- 관리자가 먼저 입금 확인을 했는데 가상계좌로도 입금됐다: 홀딩 지갑에는 기록되고, 정산은 경고를 남겨요.
- 입금 오류(판매자 계좌의 송금 한도 초과, 네트워크 문제 등)로 토스가 입금 완료를 입금 대기로 되돌렸다: 결제는 장부를 그대로 두고 에러 기록을 남겨요.
  홀딩 지갑에는 받지 못한 돈이 남아 있고 정산은 이미 회수를 끝냈으므로, 관리자가 판매자에게 다시 입금을 안내하고 장부와 청구를 맞춰요 (11/10 결정).

**정하지 않은 것 · 확인하지 못한 것**

- 판매자가 두 번 낸 돈(바로 위 세 번째 경우)을 어떻게 돌려줄지 정하지 않았어요.
- 입금 오류를 자동으로 되돌릴지(홀딩 지갑 −, 회수 입금을 입금 대기로, 정산에 입금 취소 메시지 → 청구 다시 열기) 정하지 않았어요. 정산 쪽 처리가 함께 필요해요.
- 테스트 결제내역에서 입금 오류를 일으키는 방법은 찾지 못했어요. 상태가 되돌아가는 동작은 토스 웹훅 이벤트 문서가 근거예요.
- 관리자 입금 확인 버튼을 남길지는 정산 담당이 정해요.
- 토스가 같은 주문번호로 다시 발급할 때 거절하는지, 같은 계좌를 주는지 문서로 확인하지 못했어요. 발급 전 조회로 어느 경우든 계좌를 하나로 지켜요.
- 「다른 금액은 입금할 수 없다」는 토스 안내 글이 근거예요. 테스트의 「입금처리」 버튼은 정확한 금액만 넣어서 직접 확인할 수 없어요.
