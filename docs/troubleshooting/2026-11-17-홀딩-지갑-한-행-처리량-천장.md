# 정산이 섞이면 결제 처리량이 70%로 떨어지는 원인을 홀딩 지갑 한 행으로 좁히고, 측정 근거로 고치지 않기로 정함 (2026-11-17)

- Linear: BUK-11
- 찾은 곳: 예치금 부하 측정 [연습](../measurements/2026-11-16-예치금-부하.md) 4·5장, [기준선](../measurements/2026-11-17-예치금-부하-기준선.md) P3, [전후](../measurements/2026-11-17-예치금-부하-전후.md) 6장, [2차](../measurements/2026-11-19-예치금-부하-2차.md) 5장
- 고친 코드: 없음 (판단과 다음 측정 항목만 남김)

## 1. 한 줄 요약

결제가 쉬지 않고 들어오는 중에 정산 지급을 섞으면 결제 처리량이 앞 1분의 70%로 떨어졌어요(판정 기준 80% 미달).
측정을 바꿔 가며 원인을 CPU·DB 연결이 아니라 **모든 결제와 정산이 함께 잠그는 홀딩 지갑 한 행**으로 좁혔어요.
떨어진 처리량도 필요량의 몇 배이고 실제 정산 지급은 새벽 4시 배치라서, 돈 구조를 바꾸는 수정은 하지 않기로 정하고 근거와 남은 확인을 기록했어요.

## 2. 증상

| | 기대 (판정 기준 P3) | 실제 |
|---|---|---|
| 정산 지급(초당 20건)이 섞인 1분의 결제 처리량 ÷ 앞 1분 | 80% 이상 | **기준선 72%, A 70%, B 69%** (3회 중앙값) |
| 같은 1분의 결제 p99 | 1초 아래 | 기준선 227ms, A 98ms (통과) |
| 같은 1분의 정산 지급 p95 | | 기준선 최대 1.3초 |

- 회차마다 51~79%로 흔들렸어요. 기준선 3회차 그래프로는 결제 처리량이 초당 120~250건에서 65~175건으로 떨어졌어요.
- 결제 응답 시간은 기준 안이에요. **처리량 조건 하나로만** 문제 있음이 됐어요.
- 정산 지급 쪽이 1.3초까지 늦어졌는데, 가짜 은행 호출은 평균 40ms 아래였어요. 늦어진 곳은 은행이 아니었어요.

**배경: 홀딩 지갑은 왜 한 행인가**
- 결제 대금은 정산 전까지 홀딩 지갑 하나에 모여요. 결제는 회원 지갑과 홀딩 지갑을, 정산 지급은 홀딩 지갑과 시스템 지갑을 잠가요.
- 세미 프로젝트 때 지갑을 늘 회원 ID 오름차순으로 잠그게 고정하고, 결제·환불·정산을 섞은 k6 부하로 락 대기 8,469번 속에서 데드락 0건을 확인했어요.
- 그때부터 「모든 돈 이동이 한 행에서 줄을 서면 병목이 되지 않을까」가 남은 질문이었어요.

## 3. 가설

| 번호 | 가설 | 맞으면 보여야 할 것 | 판정 |
|---|---|---|---|
| H1 | 결제가 막히는 건 계산(CPU)이 아니라 무언가를 기다리며 줄을 서기 때문이에요 | 막힐 때 CPU는 낮고, 대기(DB 연결·행 락)가 치솟음 | **맞음** (연습: 초당 200·400건에서 CPU 8% 아래, DB 연결 10개 모두 참, 결제의 57%가 행 락 대기) |

| H3 | 모든 결제가 잠그는 홀딩 지갑 한 행이 천장이에요 | 부르는 쪽을 늘려도 처리량은 그대로, 응답만 늘어남. 행 락 대기 수 ≈ 결제 수 | **맞음** (1차는 정황. 2차 잠금 스냅샷에서 기다린 행이 홀딩 지갑(id 2)인 것을 확인했어요. 다만 초당 400건에서 무너지는 건 락이 아니라 CPU 상한이었어요) |
| H4 | 정산 지급이 홀딩 지갑 잠금을 결제보다 자주·오래 쥐어서 결제 처리량을 떨어뜨려요 | 정산이 섞이면 행 락 대기가 늘고 결제 처리량이 떨어짐. 은행 호출은 잠금 밖 | **맞음 (정황)** 정산 한 건이 잠금을 쥐는 시간은 재지 않았어요 |
| H5 | 실제 결제 속도(필요량 근처)에서는 정산이 섞여도 결제가 느려지지 않아요 | 결제를 초당 50건으로 고정하면 정산이 섞여도 처리량·응답이 그대로 | **맞음** (연습 B-2: 초당 50건 그대로, p95 13ms) |

H5가 판단을 바꿨어요. 70%로 떨어진 건 **결제가 천장까지 밀어붙일 때의 처리량**이고, 실제 들어올 속도에서는 드러나지 않았어요.

### 원인

1. 결제(`CashSupport.lockCustomerAndHoldingWallets`)는 회원 지갑과 홀딩 지갑 행을 잠가요. 회원은 매번 다르지만 홀딩 지갑은 모든 결제가 같은 한 행이에요.
2. 그래서 결제는 홀딩 지갑 앞에서 한 줄로 서요. 처리량 천장은 「1 ÷ 한 건이 홀딩 지갑을 쥐는 시간」이에요. 연습의 초당 약 190건이면 한 건이 약 5ms씩 쥔 셈이에요.
3. 정산 지급(`CashPayoutUseCase`)도 같은 행을 잠가요. 한 건에 두 번 잠그고, 첫 잠금 안에서 수수료 기록·원장 세 줄·송금 기록까지 해서 결제보다 오래 쥐어요.
4. → 결제가 천장까지 들어오는 중에 정산이 끼면, 같은 줄에 더 무거운 일이 섞여 결제 몫이 줄어요.

### 영향 범위

- 홀딩 지갑을 잠그는 일은 결제, 결제 취소·환불, 정산 지급, 판매자 회수 입금이에요. 모두 이 한 행의 줄을 함께 써요.
- 1차에서는 회차 전체에서 가장 오래 기다린 행 락이 A·B 6회 중 5회 2초를 넘었어요. 주문은 예치금을 2초까지만 기다려서, 그보다 오래 락을 기다린 결제는 주문 쪽에서 「결과 모름」이 돼요.
  B-1 한계(초당 400건까지)에서 나온다고 추정했는데, **2차에서 틀린 것으로 나왔어요.** 시나리오마다 따로 읽으니 2초를 넘은 곳은 B-1 한계(0.6초 아래)가 아니라 **막 띄운 직후 예열**(사용자 2명, 최대 2.6초)이었어요.
  JFR로 보니 홀딩 지갑을 잠근 결제가 그 2초 동안 클래스를 처음 읽고 JIT 컴파일을 하고 있었어요. 붐벼서가 아니라 「첫 실행 비용」과 「홀딩 지갑을 먼저 잠그는 순서」가 겹친 거예요.

## 5. 고친 내용

**코드는 고치지 않았어요.** 대신 아래를 했어요.
- 판정 결과(P3 문제 있음)는 그대로 두고, 고치지 않는 근거를 [전후 측정 문서](../measurements/2026-11-17-예치금-부하-전후.md) 6장에 숫자로 남겼어요.
- 확인하지 못한 두 가지(기다린 행이 정말 홀딩 지갑인지, 2초 넘는 락이 어느 시나리오에서 나오는지)를 [2차 측정 판정 기준](../measurements/2026-11-18-예치금-부하-2차-판정기준.md)에 넣었어요. 시나리오마다 잠금 스냅샷과 SQL별 잠금 대기를 따로 읽게 했어요.
- 2초 넘는 락이 B-1 한계 밖에서도 나오면 「락 대기 제한 + 503 응답」을 검토하기로, 판단 기준을 측정 전에 정해 두었어요.
- 2차 결과 2초 넘는 락은 예열에서 나왔어요. 그래서 [2차 고칠 것](../measurements/2026-11-20-예치금-부하-2차-고칠것.md) ④에서 고르는 순서를 정했어요. 운영 지표로 배포 직후 결제가 느려지는지 먼저 보고, 보이면 「홀딩 지갑을 커밋 직전에 잠그기」를 해요. 이 방법은 평소 잠금 시간도 줄여 이 문서의 천장에도 도움이 돼요.

### 검토한 방법

| 방법 | 장점 | 단점 | 고름 |
|---|---|---|---|
| 홀딩 지갑을 여러 행으로 나누기 | 천장이 나눈 수만큼 올라가요 | 1차 정산 뒤 환불로 모자란 홀딩 지갑을 회수금으로 채우는 구조(정책 6장)와 정산 합계 계산이 모두 바뀌어요. 돈이 움직이는 모든 경로를 다시 확인해야 해요 | |
| 정산 지급이 잠금을 쥐는 시간 줄이기 (잠금 안의 일 줄이기, 두 번 잠그기를 한 번으로) | 돈 구조는 그대로예요 | 돈이 움직이는 순서를 건드려요. 정산 한 건이 잠금을 얼마나 쥐는지 재지 않아서 얻는 효과를 미리 말할 수 없어요 | |
| DB 연결 수 늘리기 | 설정 하나예요 | 연결은 락을 기다리느라 묶인 것이라 천장이 오르지 않을 거예요(재 보지 않음) | |
| 그대로 두고 근거와 남은 확인을 기록하기 | 돈 구조를 건드리지 않아요. 한 행이라 잠금 순서가 단순해 교착이 생기지 않는 장점도 그대로예요 | 천장은 남아요. 대기열 속도가 바뀌면 다시 봐야 해요 | ✓ |

### 고른 이유

| 근거 | 숫자 |
|---|---|
| 결제 응답 시간은 기준 안 | 정산이 섞인 1분의 결제 p99 98ms (기준 1초) |
| 천장이 필요량보다 훨씬 높음 | 결제 천장 초당 246~288건(A·B의 B-1), 필요량 초당 48건(동시 종목 12개 × 종목당 초당 4명)의 5배 |
| 실제 대회 중 가장 빠른 사례도 천장 아래 | 2025 춘천마라톤 약 2만 명 3분 마감, 성공 신청만 초당 약 110건. 우리 대기열은 종목당 초당 4명이라 이 속도가 예치금까지 오지도 않아요 |
| 실제로는 정산과 결제가 거의 겹치지 않음 | 정산 지급은 매일 04:00 배치. 겹치는 건 관리자가 지급을 손으로 실행할 때뿐이에요 |
| 실제 결제 속도에서는 드러나지 않음 | 결제 초당 50건 고정이면 정산이 섞여도 처리량 그대로, p95 13ms (H5) |

정리하면, 70%는 「결제가 천장까지 밀어붙이는 중에, 실제로는 거의 없는 시각에 정산이 섞일 때」의 숫자예요. 이걸 고치려면 돈이 움직이는 구조를 바꿔야 해서, 얻는 것보다 위험이 커요.
홀딩 지갑 한 행은 병목이지만, 모든 돈 이동을 한 줄로 세워 교착을 막는 역할도 해요. 그래서 이 줄을 없애기보다 줄이 넘치지 않는지 계속 재는 쪽을 골랐어요.

- **횟수:** 기준선·A·B는 3회씩 재서 중앙값을 썼어요. 연습은 시나리오마다 1번이에요.
- 회차마다 B-2 비율이 0.51~0.79로 크게 흔들려요. 70%라는 숫자 하나보다 「80% 아래로 자주 떨어진다」로 읽어요.

## 8. 배운 점

- **처리량 문제는 「밀어붙인 모양」과 「실제 도착 모양」을 나눠 재요.** 결제를 초당 50건으로 고정했을 때는 정산이 섞여도 아무 일이 없었고, 쉬지 않고 밀어붙일 때만 70%가 나왔어요. 둘 중 하나만 쟀으면 「문제없음」이나 「심각함」 한쪽으로 잘못 읽었을 거예요.
- **부르는 쪽을 늘려도 처리량이 안 늘면 함께 쓰는 자원 한 곳이 천장이에요.** CPU가 낮고 연결이 다 찼다고 연결이 원인은 아니었어요. 연결 대기가 0인 조건(동시 4·8개)을 따로 만들어 보니 줄은 행 락에서 서고 있었어요.
- **문제 있음 판정과 고칠지는 따로 정해요.** 판정 기준은 측정 전에 정해 두고 바꾸지 않았고, 고칠지는 실제 운영 조건(정산 시각, 대기열 속도, 실제 대회 속도)과 고치는 비용을 함께 놓고 정했어요.
- **회차 전체 누적값으로 세운 추정은 시나리오별로 나눠 읽기 전까지 추정이에요.** 「2초 넘는 락은 B-1 한계에서 나온다」는 그럴듯했지만, 시나리오마다 따로 읽으니 막 띄운 직후 예열이었어요.
- **병목인 설계가 다른 문제를 막고 있을 수 있어요.** 홀딩 지갑 한 행은 처리량의 천장이지만, 모든 돈 이동을 한 줄로 세워 교착을 막아요. 없애기 전에 그 역할부터 따져요.
