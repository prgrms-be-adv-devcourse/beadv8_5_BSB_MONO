# 공용 쓰레드에서 보낸 알림이 Kafka로 나가지 않던 문제, 알림 실패 100건 → 0건 (2026-11-17)

- Linear: BUK-13
- 찾은 곳: 예치금 부하 측정 [기준선](../measurements/2026-11-17-예치금-부하-기준선.md) 6장 3번 (BUK-11)
- 고친 코드: common `NotificationKafkaSender`, board-service `BoardFileLinkSender`

## 1. 한 줄 요약

알림을 공용 ForkJoin 풀에서 Kafka로 보내고 있었어요. jar로 띄운 앱(운영과 같은 방식)에서는 이 풀의 쓰레드가 Kafka 클래스를 찾지 못해요.
그래서 그 쓰레드가 앱에서 처음으로 Kafka 보내는 객체를 만들면, 앱을 다시 띄울 때까지 그 앱의 Kafka 전송이 모두 막혀요.
Spring Boot가 만드는 작업 실행기에서 보내게 바꿨고, jar 컨테이너에서 알림 실패가 100건에서 0건이 됐어요.

## 2. 증상

| | 기대 | 실제 |
|---|---|---|
| 기한 알림 배치(대상 100명)가 보낸 알림 | 100건이 Kafka로 나감 | **100건 모두 실패**, 로그만 남고 버려짐 |
| 그 뒤 같은 앱의 다른 Kafka 전송 | 정상 | 앱을 다시 띄울 때까지 모두 실패 |

로그 (예치금, 운영 프로필, jar로 띄운 컨테이너):

```text
WARN  [onPool-worker-3] NotificationKafkaSender : 알림을 보내지 못했습니다 (버림). eventId=…, kind=CARD_CANCEL_DEADLINE,
      cause=java.util.concurrent.CompletionException: java.lang.ExceptionInInitializerError        ← 첫 건
WARN  [onPool-worker-3] NotificationKafkaSender : 알림을 보내지 못했습니다 (버림). eventId=…,
      cause=java.util.concurrent.CompletionException: java.lang.NoClassDefFoundError:
            Could not initialize class org.apache.kafka.clients.producer.ProducerConfig            ← 둘째 건부터
```

- 예치금 부하 측정 3회 모두, 첫 알림을 보내는 순간부터 알림이 전부 실패했어요(회차마다 약 11만 건).
- 로그의 쓰레드 이름 `onPool-worker-3`은 Java 공용 ForkJoin 풀(`ForkJoinPool.commonPool-worker-3`)의 쓰레드예요.
- 개발 중에는 보이지 않았어요. 이 부하 측정은 운영과 같은 jar 이미지로 돌렸어요.

## 3. 가설

오류 문구, 쓰레드 이름, 코드(`supplyAsync`에 실행기를 넘기지 않음)를 보고 재현하기 전에 세운 가설이에요.
쓰레드 이름이 처음부터 공용 풀을 가리켜서, 다른 원인 후보(Kafka 연결, 설정 값 등)는 세우지 않았어요.

| 번호 | 가설 | 맞으면 보여야 할 것 | 판정 |
|---|---|---|---|
| H1 | 알림을 공용 ForkJoin 풀에서 보내서, 그 쓰레드가 jar 안의 Kafka 클래스를 찾지 못해요 | jar에서 재현되고, 쓰레드의 클래스 로더만 바꾸면 실패가 사라짐 | **맞음** (100건 → 0건, 단위 테스트에서 시스템 클래스 로더 확인) |
| H2 | 한 번 초기화에 실패하면 앱을 다시 띄울 때까지 계속 막혀요 | 첫 건만 `ExceptionInInitializerError`, 그 뒤는 모두 `NoClassDefFoundError` | **맞음** (재현 100건 중 1건 + 99건) |
| H3 | bootRun(dev)에서는 생기지 않아요. 그래서 개발 중에 못 봤어요 | bootRun으로 같은 배치를 돌리면 실패 0건 | **확인 안 함** (비교한 bootRun 로그에 알림 전송 자체가 0건이라 비교가 안 됐어요) |
| H4 | 다른 코드가 먼저 Kafka 보내는 객체를 만들면 생기지 않아요. 그래서 띄울 때마다 다를 수 있어요 | 요청 쓰레드에서 먼저 Kafka를 보낸 뒤 알림을 보내면 실패 0건 | **확인 안 함** (코드와 원리로 추론) |

## 4. 어떻게 확인했나

| 실행 | 바꾼 것 | 본 것 | 결과 | 판정한 가설 |
|---|---|---|---|---|
| 재현 | 지금 코드 그대로 (jar, 운영 프로필) | 알림 실패 수, 예외 종류 | 100건 중 **100건** 실패 (첫 건 `ExceptionInInitializerError`, 99건 `NoClassDefFoundError`) | H2 맞음 |
| 원인 확인 실험 | 공용 풀 쓰레드에 앱 클래스 로더를 넣는 한 줄만 더함 (커밋 안 함, 되돌림) | 알림 실패 수, Kafka 보내는 객체 | **0건**, 객체가 공용 풀 쓰레드에서 만들어짐 | H1 맞음 |
| 단위 테스트 `sendsWithCallerClassLoader` | 고치기 전 코드 | Kafka를 부른 쓰레드의 클래스 로더 | 시스템 클래스 로더가 나와 실패 | H1 맞음 |
| 고친 코드 | 작업 실행기에서 보냄 | 알림 실패 수, Kafka 보내는 객체 | **0건**, 작업 실행기 쓰레드 `task-3`에서 만들어짐 | (수정 확인) |

- 컨테이너 실행은 모두 예치금 부하 측정 컨테이너(`docs/loadtest/scenario-b/container`, BUK-11 브랜치)에서 B-4(기한 알림 배치, 대상 100명)만 짧게 돌렸어요.
- 단위 테스트는 부른 쪽 쓰레드에 다른 클래스 로더를 넣고 보낸 뒤, Kafka를 부른 쓰레드의 클래스 로더가 같은지 봐요.

### 원인

1. `NotificationKafkaSender`는 커밋이 끝난 요청 쓰레드가 Kafka를 기다리지 않게 `CompletableFuture.supplyAsync(...)`로 따로 보냈어요. 실행기를 넘기지 않아서 **공용 ForkJoin 풀**에서 돌아요.
2. 공용 ForkJoin 풀의 쓰레드는 **시스템 클래스 로더**를 써요(Java가 정한 동작).
3. Spring Boot jar는 라이브러리를 jar 안의 jar로 넣고, 그 클래스는 Spring Boot의 클래스 로더만 찾을 수 있어요. 시스템 클래스 로더는 찾지 못해요.
4. Kafka 보내는 객체를 처음 만들 때 Kafka 설정 클래스(`ProducerConfig`)가 초기화되면서, 지금 쓰레드의 클래스 로더로 다른 Kafka 클래스를 찾아요.
   공용 풀 쓰레드에서는 찾지 못해 **초기화가 실패**해요(`ExceptionInInitializerError`).
5. Java는 초기화에 실패한 클래스를 다시 초기화하지 않아요. 그 뒤로는 어느 쓰레드에서든 `NoClassDefFoundError`가 나요.
   → **앱을 다시 띄울 때까지 그 앱의 모든 Kafka 전송이 막혀요.**

확인하지 않은 부분(H3·H4):
- bootRun은 라이브러리를 jar 밖에 두고 시스템 클래스 로더로 읽어요. 그래서 공용 풀 쓰레드도 Kafka 클래스를 찾고, 개발 환경에서는 생기지 않을 거라고 봤어요.
- 다른 코드가 먼저 요청·스케줄러 쓰레드에서 Kafka 보내는 객체를 만들어 두면 이 문제는 생기지 않을 거예요. 객체를 한 번 만들면 다시 쓰기 때문이에요.
  그렇다면 **앱이 뜬 뒤 첫 Kafka 전송이 무엇이냐에 따라** 생기기도 하고 안 생기기도 해서, 운영에서 띄울 때마다 다를 수 있어요.

### 영향 범위

| 서비스 | 공용 풀에서 보내는 것 | 막히면 함께 막히는 것 |
|---|---|---|
| 예치금 | 알림(기한 알림, 환급 완료) | 회수 입금 메시지(정산이 회수를 끝내는 데 필요) |
| 주문 | 알림 | 아웃박스 릴레이 메시지 |
| 회원 | 알림 | 회원 이벤트 아웃박스 |
| 문의 | 알림 | |
| 게시판 | 글 사진 연결 요청(`BoardFileLinkSender`) | 게시판 아웃박스 |

코드로 본 범위예요. 운영에서 실제로 막혀 있었는지는 보지 않았어요(운영 로그 확인 안 함).

## 5. 고친 내용

`supplyAsync`에 Spring Boot가 만드는 작업 실행기(`applicationTaskExecutor`)를 넘겨요.
이 실행기의 쓰레드는 처음 일을 넘긴 쓰레드(요청·스케줄러·Kafka 리스너 쓰레드)가 만들어서, 그 쓰레드의 앱 클래스 로더를 이어받아요.

```diff
- CompletableFuture.supplyAsync(() -> kafkaTemplate.send(record(event)))
+ CompletableFuture.supplyAsync(() -> kafkaTemplate.send(record(event)), taskExecutor)
```

- `NotificationKafkaSender`(common)와 `BoardFileLinkSender`(게시판) 두 곳을 고쳤어요.
- 문의 서비스 테스트가 공용 풀이 끝나기를 기다리던 코드를 작업 실행기를 기다리게 바꿨어요(`InquiryTestBase`).
- 보내지 못하면 로그만 남기고 버리는 동작, 부른 쪽에 예외를 던지지 않는 동작은 그대로예요.

### 검토한 방법

| 방법 | 장점 | 단점 | 고름 |
|---|---|---|---|
| Spring Boot 작업 실행기에서 보내기 | 이미 모든 서비스에 있는 실행기라 새 설정이 없어요. 쓰레드 수가 정해져 있고 앱을 내릴 때 남은 일을 정리해요 | 다른 비동기 작업과 같은 실행기를 함께 써요 | ✓ |
| 공용 풀은 두고, 보내기 전에 쓰레드의 클래스 로더를 바꿔 넣기 | 한 줄이면 돼요. 원인 확인 실험에서 효과를 봤어요 | 공용 풀을 쓰는 곳마다 같은 줄을 기억해서 넣어야 하고, 빠뜨리면 다시 같은 문제가 나요 | |
| 요청 쓰레드에서 바로 보내기 | 쓰레드를 바꾸지 않아 클래스 로더 문제가 없어요 | Kafka가 멈추면 요청이 `max.block.ms`(기본 60초)까지 멈춰요. 따로 보내게 한 이유가 이거였어요 | |
| 앱이 뜰 때 Kafka 보내는 객체를 미리 만들기 | 보내는 코드를 바꾸지 않아요 | 증상만 가려요. 공용 풀에서 다른 라이브러리 클래스를 처음 쓰면 같은 문제가 또 나요 | |

### 고른 이유

원인은 실행기를 비워 둔 것 자체였어요. 그 자리를 앱 클래스 로더를 쓰는 실행기로 채우면, 쓰는 곳마다 따로 기억할 것이 남지 않아요.
Spring Boot가 모든 서비스에 이미 만들어 두는 실행기라 설정을 더하지 않아도 되고, 원래 코드 주석도 「전용 실행기로 바꾼다」였어요.
클래스 로더를 바꿔 넣는 방법은 원인을 확인하는 데는 좋았지만, 같은 실수를 막아 주지 못해서 고르지 않았어요.

## 8. 배운 점

- **bootRun에서 통과해도 jar에서 깨질 수 있어요.** 클래스 로더가 다르기 때문이에요. 쓰레드를 직접 고르는 코드(공용 풀, `parallelStream`, 직접 만든 쓰레드)는 jar로 띄운 컨테이너에서 한 번 확인해요.
- 비동기로 보낼 때는 실행기를 비워 두지 않고 Spring의 작업 실행기를 넘겨요. 실행기를 넘기지 않은 `CompletableFuture.supplyAsync`·`runAsync`는 공용 풀에서 돌아요.
- 이번 문제는 부하 측정을 운영과 같은 jar 이미지로 했기 때문에 보였어요. 측정 로그의 경고도 숫자만큼 함께 봐요.
- 「다른 환경에서는 안 생긴다」를 비교할 때는, 비교한 로그가 그 코드를 실제로 지났는지부터 봐요. 이번에 비교한 bootRun 로그에는 알림 전송이 0건이라 아무것도 증명하지 못했어요.
