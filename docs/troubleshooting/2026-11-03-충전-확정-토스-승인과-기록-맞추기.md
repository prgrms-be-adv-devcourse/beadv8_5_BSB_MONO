# 충전 확정에서 토스 승인과 우리 기록이 어긋나던 틈을 단계별로 막아, 돈은 빠졌는데 적립되지 않던 충전 0건 (2026-10-18 ~ 11-03)

- Linear: PRO-215 (PR #168), PRO-200 (PR #169), BUK-8 (PR #300)
- 찾은 곳: 충전 확정 재현 테스트, 세미 프로젝트 정리 「충전 승인(confirm) 하나를 신뢰할 수 있게 만들기까지」의 남은 질문, 노션 「충전 : cash-service와 PG사 정합성 맞추기」
- 고친 코드: cash-service `CashChargeConfirmUseCase`, `TossPaymentClient`, `WalletCharge`·`ChargeStatus`, 재확인 배치. 커밋 `c427dc187`(10/18), `225fe029c`(10/18), `229a6d434`(10/19), `3d173bfc5`(11/03), `a3ccea7e1`(11/03)

## 1. 한 줄 요약

충전 확정은 「토스 승인 → 예치금 적립」인데, 토스는 다른 회사 시스템이라 우리 DB 트랜잭션으로 함께 묶을 수 없어요. 그래서 토스는 승인했는데 우리 기록은 없거나 실패로 남는 틈이 세 군데 있었어요.
① 토스를 기다리는 긴 트랜잭션이 다른 거래와 충돌해 통째로 롤백되던 것은 토스 호출을 트랜잭션 밖으로 빼서, ② 응답을 못 받은 충전을 실패로 단정하던 것은 「확인 중」 상태와 토스 재조회로, ③ 승인 직후 서버가 죽으면 기록이 없던 것은 「처리 중」을 먼저 커밋하고 재확인 배치로 막았어요.
토스는 승인했는데 응답이 끊기거나 이상하게 온 세 장면 60건에서, 실패로 기록된 충전이 60건(600,000원 미적립)에서 0건이 됐어요.

|---|---|---|---|

| H4 | 토스 호출을 트랜잭션 밖으로 뺀 뒤에는, 승인 직후 서버가 죽으면 우리 DB에 결과를 모르는 충전을 찾을 단서가 없어요 | 승인 직후 멈춘 충전을 다시 찾을 상태값이 없음 | **맞음** (맞출 수단 없음, 테스트 0개) |

- H1을 고친 것(10/18)이 H4의 틈을 더 분명하게 만들었어요. 한 트랜잭션일 때는 실패하면 통째로 롤백됐지만, 나눈 뒤에는 「승인 → 저장」 사이가 비어요.
- H3의 원인(모름을 실패로 봄)은 처음 만든 날(10/15)부터 있었어요. 세미 프로젝트 정리(10/22)에서 「재조회까지 실패하면 카드에선 돈 빠짐 + 우리 기록은 실패로 남는다」를 남은 문제로 적어 두었고, 최종 프로젝트에서 막았어요.

### 원인

1. **토스 승인과 우리 DB 저장을 한 트랜잭션으로 묶을 수 없어요.** 우리 DB가 롤백돼도 토스의 승인은 되돌아가지 않아요.
2. 처음 코드는 「지갑 읽기 → 토스 승인 → 지갑 반영」을 한 트랜잭션에서 했어요. 지갑에는 낙관적 락(`@Version`)이 있었는데, 토스를 기다리는 동안 트랜잭션이 길게 열려 있어서 그 사이 다른 거래가 지갑을 바꾸면 커밋 때 충돌로 롤백됐어요. → 토스는 승인, 우리 기록은 없음 (H1).
3. **타임아웃은 실패가 아니라 「모름」이에요.** 그런데 토스 응답을 「승인」과 「그 밖」으로만 나눠, 응답 없음·5xx·「이미 처리됨」·「처리 중」도 실패로 기록했어요. → 토스가 실제로 승인했으면 돈은 빠졌는데 실패로 남음 (H2·H3).
4. 토스를 트랜잭션 밖으로 빼면 「승인 → 저장」 사이에 틈이 생겨요. 이 틈에서 서버가 죽으면 결과를 모르는 충전을 다시 찾을 단서가 없었어요 (H4).

### 영향 범위

- 충전 확정 하나예요. 어느 틈이든 결과는 「카드에서 돈이 빠졌는데 예치금은 없음」이에요.
- 사용자가 실패 화면을 보고 다시 결제하면 카드에서 두 번 빠져요.

**① 긴 트랜잭션 롤백 (10/18)**

| 방법 | 장점 | 단점 | 고름 |
|---|---|---|---|
| 지금 구조를 두고, 충돌하면 메서드 전체를 재시도 | 코드가 거의 그대로예요 | 롤백으로 「처리 중」 기록까지 사라져, 재시도가 **이미 승인된 결제를 토스에 다시 요청**해요. 돈을 잃는 문제를 중복 승인 문제로 바꿀 뿐이에요 | |
| 승인과 반영을 나누고, 반영이 실패하면 토스에 결제취소를 보내는 보상(Saga) | 반영 실패를 자동으로 되돌려요 | 결제취소마저 실패할 때를 대비한 아웃박스·재시도 장치가 또 필요해요. 잠깐의 DB 장애마다 멀쩡한 결제가 「승인 → 바로 취소」로 카드 내역에 남아요 | |
| 토스를 트랜잭션 밖으로 빼고, 반영만 짧은 트랜잭션에서 비관적 락 | 주문 결제에서 이미 쓰던 잠금 방식을 다시 써요. 잠금 구간이 「토스 대기 전체」에서 「지갑 쓰는 순간」으로 줄어요 | 「승인 → 저장」 사이 틈이 생겨 따로 막아야 해요 (→ H4) | ✓ |

### 고른 이유

세 번의 선택 모두 같은 기준이었어요. **「풀어야 할 문제가 무엇인가」에 맞는 가장 작은 장치를 고른다.**
- 롤백 문제는 분산 트랜잭션이 아니라 cash 안의 잠금 순서 문제라, Saga 대신 잠금 범위를 바로잡았어요.
- 모름 문제는 메시지 전달이 아니라 외부 결과 확인 문제라, 아웃박스 대신 상태값과 조회를 골랐어요. 「할 일을 먼저 DB에 남긴다」는 생각은 아웃박스와 같지만, 메시지 발행이 아니라 외부 결과 확인에 썼어요.
- 응답 유실은 드문 예외라 Kafka의 처리량이 필요 없고, 기준을 DB 하나로 두는 쪽이 운영하기 쉬웠어요.

| 승인 후 「다른 요청이 처리 중」 (20건) | 20건 실패, 0원 | **실패 0건, 200,000원 적립** |
| 승인 후 「이미 처리됨」 + 조회 실패 (20건) | 20건 실패, 0원 | 20건 확인 중 → **재확인 배치 1번에 200,000원 적립** |
| 승인 직후 서버가 죽어 처리 중으로 멈춤 | 맞출 수단 없음 | 2분 뒤 재확인 배치가 완료로 맞춤 |
| **합계 (세 장면 60건)** | **60건 실패, 600,000원 미적립** | **0건, 600,000원 모두 적립** |

| 충전·토스 관련 테스트 수 | 10/15 14개 → PR #300 뒤 49개 → 지금 71개 (이후 금액 한도·결제취소 테스트 포함) |

- **기준선:** 세 장면은 「확인 중」을 넣기 전 코드(11/03 전)와 PR #300 직후 코드를 각각 돌렸어요. 롤백 장면은 10/18 수정 전후예요.
- **조건:** 가짜 토스(Mockito)로 양쪽에 같은 응답을 주고 결과만 셌어요. 실제 토스 테스트 키로는 정상 승인 흐름만 확인했고, 느린 응답·타임아웃은 재현하지 못했어요.
- **테스트가 바뀐 과정:** 처음 테스트는 「타임아웃이면 실패」, 「이미 실패면 토스를 다시 부르지 않음」을 기대하고 있었어요. 고친 단계마다 이 기대를 「모르면 조회」, 「조회도 실패면 확인 중」으로 바꿨어요.

## 8. 배운 점

- **응답을 못 받은 것은 실패가 아니라 모름이에요.** 상태를 「성공·실패」 둘로만 두면 모름이 실패 쪽으로 새요. 「확인 중」을 상태로 따로 두니 실패는 확실할 때만 쓰게 됐어요.
- **느린 외부 호출을 트랜잭션 밖으로 빼면 그 사이 틈을 상태값으로 메워야 해요.** 트랜잭션을 나눠 롤백 문제를 고치자 「승인 → 저장」 사이 틈이 생겼고, 「처리 중을 먼저 커밋」으로 그 틈을 DB에 남겼어요. 같은 상태가 동시 요청의 토스 중복 호출도 막았어요.
- **패턴 이름보다 풀 문제를 먼저 적어요.** Saga·아웃박스·Kafka 재시도는 모두 그럴듯했지만, 문제를 「cash 안의 잠금 순서」, 「외부 결과 확인」, 「드문 예외」로 적고 나니 더 작은 장치로 충분했어요.
- **기대값이 틀린 테스트는 버그를 지켜요.** 「타임아웃이면 실패」를 기대하던 테스트가 계속 통과하고 있었어요. 고칠 때는 코드보다 테스트의 기대부터 바꿨어요.
- **남은 문제를 적어 두면 다음 단계의 출발점이 돼요.** 세미 때 Q&A에 적은 「재조회까지 실패하면 실패로 남는다」가 최종 때 확인 중 상태와 재확인 배치의 시작이었어요.
