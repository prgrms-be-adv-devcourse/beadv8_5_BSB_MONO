# 같은 충전에 몰린 동시 확정 요청의 토스 승인 호출을 평균 6.55번 → 1번으로 줄임, 결과는 그대로 (2026-10-30)

- Linear: BUK-7 (PR #264)
- 찾은 곳: 충전 확정을 트랜잭션 밖으로 나눈 뒤(`c427dc187`, 10/18) 동시성 테스트 로그. 노션 「충전 confirm 동시 요청 시 Toss 중복 호출 줄이기」
- 고친 코드: cash-service `CashChargeConfirmUseCase`, `ChargeStatus`, `WalletCharge` (커밋 `232dd0cea`, 테스트 `1208e3566`), 대기 예산 조정 `dadc1839d`, `41e7ed514`

## 1. 한 줄 요약

결제창에서 돌아온 화면의 새로고침·중복 클릭으로 같은 주문번호의 충전 확정이 동시에 오면, 요청마다 토스 승인을 불렀어요. 돈은 재조회 복구로 한 번만 들어갔지만 토스에 불필요한 승인 요청이 나갔어요.
지갑 잠금 안에서 충전 행을 「처리 중」으로 먼저 차지한 요청만 토스를 부르고, 뒤 요청은 그 결과를 기다려 같은 응답을 받게 바꿨어요.
동시 10건 × 20번 반복에서 토스 승인 호출이 평균 6.55번에서 매번 1번이 됐고, 응답 결과와 잔액·장부는 전후가 같아요. 대신 뒤 요청이 기다리는 시간이 생겨, 그 예산을 측정에 맞춰 세 번 고쳤어요.

## 2. 증상

| | 기대 | 실제 (바꾸기 전, 20번 반복) |
|---|---|---|
| 같은 주문번호 동시 확정 10건의 토스 승인 호출 | 1번 | 토스 지연 0ms: 평균 **6.55번** (최소 1 · 중앙값 7 · 최대 10) |
| | | 토스 지연 300ms: **10번** (20번 모두) |
| 응답 결과 | 10건 모두 충전 완료 | 10건 모두 충전 완료 |
| 잔액 · 충전 기록 · 장부 | 1만 원 · 1건 · 1줄 | 1만 원 · 1건 · 1줄 |

- 돈은 맞았어요. 뒤 요청이 토스에서 「이미 처리된 결제」로 거절되면 결제를 다시 조회해 완료로 맞추는 복구 경로가 있었어요.
- 줄여야 할 것은 **토스로 나가는 중복 승인 요청**이었어요. 실제 토스 응답은 수백 ms라, 동시 요청은 거의 전부 중복 호출이 돼요.
- 세미 프로젝트 정리(10/22)에서는 「돈은 안전하고, 구조를 또 바꾸는 비용이 크다」며 이 문제를 일부러 미뤘어요. 최종 프로젝트에서 다시 꺼내 고쳤어요.
- 앞서 10/19에는 이 동시 요청 사이에서 진 쪽의 실패 기록이 이긴 쪽의 완료 기록을 덮는 문제(`229a6d434`)를 고쳤어요. 동시 확정은 이미 한 번 문제를 낸 경로였어요.

## 3. 가설

| 번호 | 가설 | 맞으면 보여야 할 것 | 판정 |
|---|---|---|---|
| H1 | 「이미 완료인지」 확인하는 짧은 트랜잭션과 토스 호출이 나뉘어 있어서, 동시 요청이 모두 「아직 완료 아님」을 보고 각자 토스를 불러요 | 토스 응답이 느릴수록 중복 호출이 늘어남. 토스가 오래 걸리면 10건 모두 부름 | **맞음** (0ms 평균 6.55번 → 300ms 10번) |
| H2 | 중복 호출이 돈 문제로 이어져요 | 잔액·충전 기록·장부가 어긋남 | **틀림** (전후 모두 매번 1만 원 · 1건 · 1줄) |

H2가 틀려서 이 작업은 버그 수정이 아니라 **결과는 그대로 두고 바깥 호출을 줄이는 개선**이 됐어요. 그래서 「결과가 전후 같다」를 측정 항목에 함께 넣었어요.

| 실행 | 바꾼 것 | 본 것 | 결과 | 판정한 가설 |
|---|---|---|---|---|

| 측정 테스트, 바꾸기 전 코드 (`15158100`) | 토스 지연 0ms·300ms, 각 20번 | 10건당 토스 승인 호출, 응답, 잔액·기록·장부 | 6.55번 / 10번, 돈은 맞음 | H1 맞음, H2 틀림 |
| 측정 테스트, 바꾼 뒤 코드 (`da8b5aa4`) | 같음 | 같음 | 매번 1번, 돈은 맞음 | (수정 확인) |
| `ChargeConfirmConcurrencyTest` | 바꾼 뒤 코드 | 동시 요청 중 토스를 부른 수 | 1번 | (회귀 방지) |

측정 테스트(`ChargeConfirmDuplicateCallMeasureTest`)는 같은 회원·같은 주문번호로 쓰레드 10개가 출발 신호 하나를 기다렸다 동시에 확정을 보내요. 가짜 토스는 처음 승인만 성공시키고, 그 뒤 승인은 「이미 처리된 결제」로 거절해요.

### 원인

1. 10/18에 토스 승인을 트랜잭션 밖으로 뺐어요. 토스를 기다리는 동안 다른 거래와 버전 충돌로 충전 기록을 잃는 문제를 막으려는 것이었어요.
2. 그 결과 흐름이 「짧은 트랜잭션에서 이미 완료인지 확인 → 트랜잭션 밖에서 토스 승인 → 짧은 트랜잭션에서 결과 반영」이 됐어요.
3. 첫 단계에서 「누가 토스를 부르는 중」이라는 표시가 없었어요. → 동시에 온 요청은 모두 「아직 완료 아님」을 보고 각자 토스를 불렀어요.
4. 토스가 느릴수록 앞 요청이 완료를 기록하기 전에 뒤 요청이 첫 단계를 지나가서, 중복 호출이 늘었어요.

### 영향 범위

- 충전 확정 하나예요. 돈은 맞지만 토스에 중복 승인 요청이 나가고, 토스가 연속 요청을 제한하면 정상 요청까지 거절될 수 있어요.

## 5. 고친 내용

충전 상태에 「처리 중(`IN_PROGRESS`)」을 더했어요. 첫 단계에서 지갑을 잠근 채 충전 행을 확인하고, 아직 아무도 차지하지 않았으면 처리 중으로 바꾼 뒤 커밋해요. 이 요청만 토스를 불러요.

```text
지갑 잠금 → 충전 행 확인
  ├ 완료         → 기존 결과로 바로 응답 (같은 요청 다시 와도 같은 답)
  ├ 처리 중      → 토스를 부르지 않고, 앞 요청의 결과를 기다렸다 같은 응답
  └ 없음·실패    → 처리 중으로 바꾸고 커밋 → 이 요청만 토스 승인 → 결과 반영
```

- 잠금을 잡은 채 토스를 부르지 않아요. 첫 단계를 먼저 커밋해야 뒤 요청이 처리 중을 봐요.
- 처음 계획은 뒤 요청에 바로 409(처리 중)를 주는 것이었어요. 실제로는 **앞 요청이 끝날 때까지 기다렸다 같은 결과를 주게** 바꿨어요. 평소에는 앞 요청이 금방 끝나서, 새로고침한 사용자가 409 대신 완료를 받는 쪽이 맞았어요. 기다림 예산을 넘기면 그때 409를 줘요.

**동작이 같다는 근거**
- 측정에서 전후 모두 매번 10건 모두 충전 완료, 잔액 1만 원 · 충전 기록 1건 · 장부 1줄이었어요. 「처리 중」 응답은 0건이었어요.
- 기존 동시성 테스트 3개(`ChargeConfirmConcurrencyTest`, `ChargeConfirmFailedThenCompletedRaceTest`, `ChargeConfirmMoneyLostConcurrencyTest`)를 선점 흐름에 맞게 고치고, 동시 요청 중 하나만 토스를 부르는지 검증을 더했어요.

### 검토한 방법

| 방법 | 장점 | 단점 | 고름 |
|---|---|---|---|
| 그대로 두고 재조회 복구에 맡기기 | 돈은 이미 맞아요 | 토스에 중복 승인이 계속 나가요. 토스 지연이 길면 동시 요청 거의 전부예요 | |
| Redis 분산 락 (`SET NX PX` + 고유값 비교 삭제) | 토스를 부르기 전에 한 요청만 통과시켜요 | TTL이 토스 응답보다 짧으면 호출 도중 풀려 중복이 다시 생기고, 길면 서버가 죽었을 때 그 주문이 오래 막혀요. Redis 장애 때 막을지 통과시킬지 따로 설계해야 해요. 결국 「이미 완료인지」는 DB에서 다시 봐야 해요 | |
| DB 충전 행을 지갑 잠금 안에서 「처리 중」으로 선점, 뒤 요청은 바로 409 | 의존성이 늘지 않아요 | 평소에도 새로고침한 사용자가 완료 대신 409를 받아요 | |
| DB 충전 행 선점, 뒤 요청은 결과를 기다렸다 같은 응답 | 의존성이 늘지 않고, 평소에는 뒤 요청도 완료를 받아요 | 뒤 요청이 기다리는 시간이 생기고, 그 예산을 정해야 해요 | ✓ |

### 고른 이유

Redis 락만으로는 막을 수 없는 구간이 남았어요. 토스 응답이 TTL보다 길거나 Redis가 장애면 락이 풀리고, 그 순간의 중복 호출을 막으려면 결국 DB에 「처리 중」을 둬야 해요. 그러면 DB 상태만으로 충분하고 Redis는 한 겹 더 얹는 일이 돼요.
DB는 지갑 잠금 때문에 이미 필수 의존성이라 새로 늘어나는 장애 지점이 없어요. 또 결과를 모르는 충전을 뒤에서 다시 확인하는 복구도 DB 상태값을 전제로 해서, 어느 쪽을 골라도 상태값은 필요했어요.

- **기준선:** 개선 커밋 바로 앞(`15158100`)이에요. 바꾼 뒤는 측정한 날의 dev(`da8b5aa4`)라, 그 사이 들어간 다른 충전 변경(결과를 모를 때 조회로 확인하기 등)도 함께 들어 있어요.
- **조건:** 두 코드를 각각 별도 worktree에 꺼내 같은 측정 테스트를 돌렸어요. H2 메모리 DB(MySQL 모드), 가짜 토스, 바꾼 뒤 코드는 충전 이상 감지 때문에 Redis 테스트 컨테이너를 붙였어요. 뒤 요청 기다림은 테스트 값(50ms 간격, 최대 0.5초)이에요.
- **횟수:** 토스 지연 0ms·300ms 각각 20번. 처음 예열 3번은 뺐어요. 측정은 개선 뒤인 11/11에 옛 커밋을 꺼내 했어요.
- **늘어난 시간:** 뒤 요청이 50ms 간격으로 결과를 다시 확인하기 때문이에요. 중복 결제 위험을 줄이는 대가로 받아들였어요.

**대가(기다림 예산)를 측정에 맞춰 고친 과정**

| 날짜 | 기다림 예산 | 바꾼 이유 |
|---|---|---|
| 10/30 | 2초 (100ms × 20번) | 처음 값 |
| 11/02 (`dadc1839d`) | 7초 (100ms × 70번) | 우리가 정한 토스 호출 시간 제한(연결·응답 각 5초)보다 짧아서, 앞 요청이 아직 토스를 기다리는데 뒤 요청이 먼저 409를 받았어요 |
| 11/03 | 22초 (100ms × 220번) | 결과를 모를 때 결제 조회까지 하면 앞 요청이 가장 길게 19초 걸려요. 뒤 요청도 결과를 받게 그보다 길게 잡았어요 |
| 11/20 (`41e7ed514`) | **3초** (100ms × 30번) | 2차 부하 측정에서 토스가 4초 걸릴 때 같은 충전 두 번째 요청이 중앙값 8.7초 동안 요청 쓰레드를 쥐었어요. 평소(승인 1초 안팎)에는 3초 안에 결과를 받고, 느릴 때만 409로 쓰레드를 돌려줘요 |

3초 뒤 409를 받아도 돈은 맞아요. 앞 요청이 끝까지 처리하고, 프론트는 409를 「결과를 모름, 기다리세요」로 보여 주며 확정을 다시 부르지 않아요.

**토스 호출 시간 제한 5초의 근거.** 토스는 응답 대기 60초를 권하지만, 우리는 쓰레드를 오래 쥐지 않으려고 5초로 잘랐어요. 그 사이 승인된 결제는 확인 중 상태와 재확인 배치가 놓치지 않아요.
다만 5초라는 숫자 자체는 여전히 근거가 없어요. 실제 토스 승인 응답 시간 분포(p99 등)를 본 적이 없어서, 정상 승인 중 몇 %가 5초에 잘리는지 몰라요. 운영 지표로 토스 승인 응답 시간을 보면 이 값을 측정으로 정할 수 있어요.

## 8. 배운 점

- **돈이 맞는지와 바깥 호출이 맞는지는 따로 봐요.** 재조회 복구 덕분에 돈은 늘 맞았지만, 그 뒤에서 토스에 승인이 최대 10번 나가고 있었어요.
- **느린 호출을 트랜잭션 밖으로 빼면 「누가 부르는 중인지」 표시가 필요해요.** 트랜잭션이 해 주던 줄 세우기가 사라지기 때문이에요. 이번에는 그 표시를 DB 상태값으로 두었어요.
- **분산 락은 DB 상태값을 대신하지 못해요.** 락이 풀리는 순간이 있는 한 「이미 끝났는지」는 결국 원본 저장소에서 확인해야 해서, 새 의존성을 늘리지 않았어요.
- **개선이 만든 대가는 숫자로 계속 관리해요.** 기다림 예산은 한 번 정하고 끝나지 않았어요. 토스 호출 시간 제한, 결과 모름 처리, 부하 측정이 나올 때마다 근거를 붙여 2초 → 7초 → 22초 → 3초로 고쳤어요.
