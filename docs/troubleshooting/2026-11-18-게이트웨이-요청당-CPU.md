# 게이트웨이가 요청마다 연결을 새로 받느라 CPU를 쓰던 문제 (2026-11-18)

- Linear: CRU-58
- 찾은 곳: 예매 부하 테스트(11/18, 손영호) 결과의 「게이트웨이 CPU 0.56코어」
- 고칠 곳: nginx 설정 `backend/docker/nginx/upstreams.conf`, `backend/docker/nginx/routes.conf` (k8s는 같은 파일을 ConfigMap으로 씀), 게이트웨이 `k8s/base/apps/gateway.yaml`(preStop)

## 1. 한 줄 요약

nginx가 게이트웨이로 요청을 넘길 때 요청마다 TCP 연결을 새로 맺고 끊고 있었어요.
그래서 게이트웨이(Netty)가 초당 수백 번 연결을 준비하고 정리하느라 CPU를 썼어요.
nginx에 HTTP keep-alive(upstream keepalive)를 켜서 연결을 다시 쓰게 하기로 했어요.

## 2. 문제

11/18 예매 부하 테스트(운영 서버 t3.large, 2코어)에서 대기열 조회가 초당 200건을 넘자 CPU가 91%까지 올라가 지연이 기준을 넘었어요.
파드별 CPU는 게이트웨이가 **0.56코어**로 가장 컸어요.

리포트는 원인을 「요청마다 하는 JWT 검증」으로 봤어요.
하지만 JWT는 HMAC 방식이라 검증 한 번이 수십 마이크로초예요. 초당 330건이어도 0.02코어 안쪽이라 0.56코어를 설명하지 못해요.
그래서 게이트웨이 CPU가 실제로 어디에 쓰이는지부터 재기로 했어요.

## 3. 원인을 찾은 과정

### 3-1. JFR로 재려다 실패

게이트웨이에 JFR(자바에 들어 있는 CPU 기록 도구)을 켰더니 약 10초 뒤 JVM이 죽고 다시 시작됐어요(API 약 1분 멈춤).
오류는 `ShouldNotReachHere` (`SuspendedThreadTask`)였어요. JFR은 스레드에 신호를 보내 잠깐 멈추고 기록하는데, 서버 컨테이너 보안 설정(AppArmor)이 신호를 막아서 생긴 것으로 보여요.
같은 서버에서 `jcmd`도 신호가 「Permission denied」로 막혔어요.
→ 운영 서버에서는 신호를 쓰는 프로파일러(JFR, async-profiler)를 쓸 수 없어요. 보안 설정은 바꾸지 않았어요.

### 3-2. 조건 하나만 바꾼 부하로 비교

프로파일러 대신 게이트웨이 컨테이너의 CPU 누적값(`/sys/fs/cgroup/cpu.stat`의 `usage_usec`)을 5초마다 기록하고, 부하를 걸었어요.

| 실행 | 보낸 요청 | 게이트웨이 CPU | 요청 1건당 CPU |
|---|---|---|---|
| 토큰 없이 공개 주소(`/api/v1/product/races/1`) 조회, 2분 30초 | 초당 161건 | **0.48코어** | 약 3ms |

토큰이 없으면 게이트웨이는 JWT 검증과 로그아웃 확인(Redis)을 건너뛰어요.
그런데도 CPU가 리포트의 0.56코어에 가깝게 나왔어요.
→ 게이트웨이 CPU의 대부분은 JWT 검증이 아니라 **요청을 받아 넘기는 기본 비용**이에요.

### 3-3. 기본 비용이 큰 이유

게이트웨이 지표(`/actuator/prometheus`)와 nginx 설정을 봤어요.

- GC에 쓴 시간은 게이트웨이 전체 CPU의 약 3%였어요. GC는 원인이 아니에요.
- 요청 1건마다 메모리를 약 130KB씩 새로 잡았어요. 단순한 중계치고는 많아요.
- nginx의 `upstream gateway`에 `keepalive`가 없고, `proxy_http_version 1.1`도 없었어요.
  nginx는 이 설정이 없으면 뒤쪽 서버로 HTTP/1.0과 `Connection: close`를 보내요.
  → **요청마다 연결을 새로 맺고, 응답 뒤 끊어요.**

게이트웨이(Netty)는 연결을 받을 때마다 그 연결 전용 버퍼와 처리 단계를 만들고, 끊기면 정리해요.
요청마다 이 일이 생기니 요청당 메모리와 CPU가 커져요.

## 4. 선택지와 비교

| 선택지 | 장점 | 단점·대가 | 예상 효과 | 작업량 |
|---|---|---|---|---|
| nginx → 게이트웨이 keep-alive | 게이트웨이와 nginx CPU가 함께 줄어요. 게이트웨이 코드는 그대로예요 | 게이트웨이 재시작 순간 POST 실패, 여러 개일 때 쏠림 (6장) | 큼 (추정) | 설정 3줄 |
| 게이트웨이 → 서비스 연결 오래 쓰기 (Tomcat `max-keep-alive-requests`) | 100건마다 다시 연결하는 일이 없어져요 | 서비스마다 설정을 넣어야 해요 | 작음 | 서비스별 1줄 |
| 응답 시간 기록 하나로 줄이기 | 요청마다 두 곳에 하던 기록이 하나로 줄어요 | 끄는 쪽 지표를 쓰는 대시보드가 비어요 | 작음 | 설정 1~2줄 |
| 로그아웃 확인(Redis) 결과를 몇 초 저장 | 요청마다 Redis를 다녀오는 일이 줄어요 | 저장한 동안 로그아웃한 토큰이 통과해요. 폴링 간격(3초)보다 길게 저장해야 효과가 있어요 | 아직 재지 않음 | 게이트웨이 코드 + 테스트 |
| Traefik이 게이트웨이로 바로 보내기 | nginx가 쓰던 0.16코어가 빠져요 | 로그인 요청 횟수 제한과 `/internal` 차단을 옮겨야 해요. 게이트웨이 CPU는 그대로예요 | 중간 | 인프라 설정 여러 개 |
| JWT 검증 결과 저장 (리포트의 개선안) | 검증을 건너뛰어요 | 줄일 비용이 원래 작아요 | 거의 없음 | 게이트웨이 코드 |

## 5. 결정

**nginx → 게이트웨이 구간에 HTTP keep-alive를 켜요.**

- 측정에서 가장 큰 비용(요청당 기본 비용)을 직접 줄이는 방법이에요.
- 설정 세 줄이라 위험이 작고, 게이트웨이 코드와 인증 정책은 바꾸지 않아요.
- 게이트웨이와 nginx 양쪽 CPU가 함께 줄어요.

바꿀 내용:

```nginx
# upstreams.conf
upstream gateway {
	server bukang-gateway:8000;
	keepalive 64;   # 쉬는 연결을 최대 64개까지 열어 둔다
}

# routes.conf 맨 위 (다른 proxy_set_header와 같은 위치)
proxy_http_version 1.1;
proxy_set_header Connection "";
```

`proxy_set_header`는 location 안에서 다시 쓰면 위에서 정한 값이 모두 사라져요. 그래서 기존 헤더 설정과 같은 위치에 넣어요.

keep-alive는 웹소켓과 달라요. 연결을 끊지 않을 뿐, 대화는 HTTP 요청-응답 그대로예요.

## 6. 감수한 것과 대응

| 단점 | 언제 생기나 | 대응 |
|---|---|---|
| 게이트웨이를 여러 개 띄우면 요청이 한쪽으로 쏠림 | k8s Service는 연결 단위로 나눠 주는데, 연결을 오래 쓰면 처음 붙은 게이트웨이로 계속 감. 지금은 게이트웨이가 1개라 생기지 않음 | nginx는 연결 하나로 1,000건(`keepalive_requests` 기본값)을 보내면 새로 맺어서, 초당 200건이면 몇 초마다 연결이 바뀌어 대략 나뉨. 고르게 나누려면 게이트웨이를 늘릴 때 파드 주소를 각각 아는 headless Service로 바꿈 |
| 게이트웨이 재시작 순간 POST가 502로 실패할 수 있음 | 열어 둔 연결로 요청을 보내는 순간 게이트웨이가 그 연결을 닫을 때. GET은 nginx가 다시 보내지만 POST는 다시 보내지 않음 | 게이트웨이에 `preStop` 5초 기다리기를 넣음. 새 연결은 새 파드로 가고, 열어 둔 연결은 끌 때까지 옛 파드가 처리함. 끄는 순간 그 연결로 온 POST가 실패할 확률은 줄지만 0은 아님. 5초와 graceful shutdown(최대 30초)이 들어가도록 `terminationGracePeriodSeconds`를 40초로 늘림. Spring Boot의 graceful shutdown(처리 중인 요청은 끝내고 꺼짐)이 기본으로 켜져 있음. 두 번 처리되면 안 되는 요청은 중복 요청 방지 키(`Idempotency-Key`)가 있어 브라우저가 다시 보내도 한 번만 처리됨. nginx가 POST를 자동으로 다시 보내는 설정(`non_idempotent`)은 켜지 않음 |
| 응답이 아주 느리면 효과가 줄어듦 | 동시에 처리 중인 요청이 쉬는 연결 수(64)를 넘으면 넘친 만큼은 예전처럼 맺고 끊음. 초당 200건에 응답 0.02초면 동시 요청은 4개 정도 | 쉬는 연결 수를 32가 아닌 64로 잡음. 근본 대응은 응답이 느려지지 않게 CPU를 줄이는 것이고, 이 변경이 그 일을 함 |

쉬는 연결은 nginx가 60초(`keepalive_timeout` 기본값) 뒤에 정리해요. 게이트웨이(Netty)에는 쉬는 연결을 먼저 끊는 설정이 없어서, 게이트웨이가 먼저 끊어 생기는 502는 평소에는 생기지 않아요.

## 8. 남은 것

- JWT 검증과 로그아웃 확인 비용은 아직 재지 않았어요. 같은 주소에 토큰을 넣고 한 번 더 돌리면 나와요.
- 측정은 맥에서 인터넷을 거쳐 보냈고, 한 번만 돌렸어요. 지연(p95)은 리포트 값과 비교하면 안 돼요.
- 요청 수 자체를 줄이는 방법(순번이 뒤쪽이면 천천히 묻기)은 대기열 서비스와 프론트의 일이라 여기서 다루지 않았어요.
