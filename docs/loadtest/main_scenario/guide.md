# 운영 부하 테스트 — 일반 가이드 + 시나리오 템플릿

team05(운영 dev, 2 vCPU·7.6GB, k3s)에서 **아무 서비스·흐름이든** 부하 테스트할 때 쓰는 공통 방법과, 시나리오마다 복사해 채우는 템플릿.
worked example(예매 몰림 funnel 실측): `runbook.md`, 측정 수치: `results.md`.

---

## A. 먼저 정할 것 — 운영에서 해야 하나?
| 방법 | 운영에 닿나 | 언제 |
|---|---|---|
| GitHub Actions `order-load-test` | 안 닿음 | 코드 변경 전후 비교 |
| 로컬 compose + k6 (`scenario-a` 등) | 안 닿음 | 로직·상대 비교 |
| **운영 k6 (이 가이드)** | 닿음 | "운영 한 대가 실제로 몇까지 버티나" |
운영은 게이트웨이·nginx·k3s·실서비스 조합이 있어 **운영에서만 알 수 있는 것**(진짜 용량)만 여기서 잰다. 공용 서버이므로 밤/한가할 때, 팀에 공지.

## B. 공통 준비 (한 번)
- **k6**: 발생기는 team05 **밖**(미니 PC/개인 PC). team05는 대상.
- **team05 SSH**(`team05` 스킬), **Grafana**(`grafana.bukang-devops.duckdns.org`, Prometheus가 전 서비스·노드 수집).
- **DB·Redis 접근**(데이터 노드 10.0.2.222, team05 경유):
  ```bash
  E=$(sudo kubectl -n crewrun exec deploy/bukang-cash-service -- printenv)
  U=$(echo "$E"|sed -n 's/^MYSQL_USER=//p'); export MYSQL_PWD=$(echo "$E"|sed -n 's/^MYSQL_PASS=//p')
  sudo -E docker run --rm -e MYSQL_PWD mysql:8.4 mysql -h 10.0.2.222 -u"$U"   # 스키마 crewrun_<svc>
  # Redis: redis:8.2 redis-cli -h 10.0.2.222 (비번 없음)
  ```
  자격증명은 파드 env에서만 읽고 화면·채팅에 출력하지 않는다.

## C. 공통 시드 원칙 (운영은 `prod` 프로필)
prod라 **가짜키 결제·실본인인증이 API로 막힘** → 상태는 DB로 직접 심는다.
- **회원**: Redis에 본인인증 결과 주입 → `POST /auth/join`(약관 **SERVICE·PRIVACY·AGE_OVER_14** 3종). nginx가 `/auth` IP당 1/s 제한 → 1.1s throttle.
- **비밀번호**: DB 통일. `member_member.password_hash`에 BCrypt `$2a$10`.
- **예치금**: DB `cash_wallet.balance`(가입 시 지갑 자동 생성). 충전 API는 토스라 막힘.
- **대상 데이터(시나리오마다 다름)**: 내 서비스 표에 직접. 대회처럼 스케줄러가 상태를 바꾸는 건 **날짜만 당기고 상태는 그대로 둬 스케줄러가 바꾸게**(이벤트가 다른 서비스에 통지됨).
- **마킹**: 이름 접두어·먼 미래 날짜·검색(ES) 차단으로 실데이터와 구분(발표 전 DB 비우므로 정리 부담은 작음).

## D. 토큰
nginx 1/s + 토큰 30분 수명 → **단계마다 쓸 인원만 로그인하고 바로 실행**(1,000명 한 번에 = 18분이라 뒤 단계 만료). `accounts/login.js`(throttle, 운영 기본) 사용, COUNT만 바꿈.

## E. 램프·판정·자동멈춤
- 단계: **smoke(도는지)** → 목표 부하 → 0→목표×N 스트레스. 낮은 데서 올려 **무너지는 지점**을 찾는다.
- 판정 기준은 **재기 전에** 적는다: 조회 p95 300ms · 쓰기 p95 1s · 실패율 1% (기본).
- **자동멈춤**: 실패율 5%(30초) + (느려지는 붕괴용) 1분 p99 5초 2분 지속. **에러율만 보지 말 것** — 에러 없이 느려지는 게 더 흔함.
- 상한(정원·입장·판매)을 넘는 **정상 거절(409 등)은 실패로 안 센다**(스크립트에서 기대 코드로).
- **RPS와 TPS 구분**: 도착률(요청/초, RPS)인지 완결 거래(예매·결제 1건, TPS)인지 보고에 명시.

## F. 측정 (서버측)
Grafana(JVM·Node·MySQL 대시보드) + `promsnap.py`(Prometheus 직접). **병목 후보 순서**:
1. **노드 CPU**(2코어) — 조회성 부하는 보통 여기서 먼저 포화. `node_cpu`.
2. **DB 커넥션풀** — `hikaricp_connections_pending`(서비스당 기본 10개). HTTP로 다른 서비스 부르며 커넥션 쥐면 고갈.
3. **게이트웨이 응답 10초 vs DB 대기 30초** 불일치, 힙·GC, 네트워크(발생기→서버).
→ 쓰기 지연이 튀는데 에러 0이면 hikari부터, 전 서비스가 동시에 느리면 노드 CPU/스왑.

## G. 함정 체크리스트 (실측에서 걸린 것)
- [ ] k6 0.54엔 `crypto.randomUUID` 전역 없음 → 고유키 직접 생성.
- [ ] arrival-rate 시나리오는 **`maxVUs` 안 주면 preAllocatedVUs에 갇혀** 목표 부하 미달(측정 무효).
- [ ] PowerShell이 k6 경고를 에러 취급 → ps1 `$ErrorActionPreference='Continue'`.
- [ ] 가입 약관 3종(AGE_OVER_14 포함) 안 넣으면 400.
- [ ] 소비성 리소스(구매자 등)는 **1회용** → 반복 시 신규 대상/계정으로.
- [ ] `--summary-export`로 단계별 P95/P99 **반드시 저장**(안 하면 기록 없음).

## H. 시나리오 템플릿 (복사해서 채우기)

```
### 시나리오: <예: product 대회 목록 조회 / payout 1차 정산 생성>
- 대상 서비스·엔드포인트:
  - <METHOD 경로> — 바디 <필수 필드> — 응답에서 다음에 쓸 값 <...>
- 부하 축: [ ] 조회(read, RPS)  [ ] 쓰기(write, TPS)  — 둘 중 뭐가 지배적인가
- 필요 시드:
  - 회원 N명 (C 공통) + <이 시나리오 전용 데이터: 어느 표에 무엇을>
  - 소비성 리소스 있나? (있으면 반복 시 신규 대상 전략)
- 인증: Bearer 토큰(D). 대기열/본인인증 등 선행 호출 있나?
- 판정 기준(재기 전): 조회 p95 <>ms / 쓰기 p95 <>ms / 실패율 <>% / 정상거절 코드 <>
- 단계(목표 /s): smoke → <load> → <stress>. 각 길이·간격.
- 예상 병목 가설: <CPU / hikari / 특정 쿼리 / 외부 호출>  + 볼 지표
- 정리: 만든 역순 삭제 SQL / 확인 SQL(합계·이중차감·음수·상한) — 넣기 전에 먼저 작성
```

채운 뒤: `accounts/login.js`로 토큰 → 내 시나리오 k6 스크립트(`scenario-a` funnel이나 `member/crew/board` 참고해 작성) → 단계 램프 + Grafana/promsnap 측정 → 결과를 `docs/loadtest/<시나리오>/` 또는 `docs-local/ops/<날짜>-<시나리오>.md`에.

## I. 이 문서를 읽은 AI에게

이 가이드를 읽었다면 **바로 작업하지 말고, 먼저 사용자에게 물어라.** 예:

> "어떤 테스트를 파생하고 싶으세요? 아니면 무엇을 도와드릴까요?
> ① **새 시나리오 설계** — H절 템플릿을 같이 채우기 (대상 서비스·엔드포인트·부하 축·판정 기준)
> ② **k6 스크립트 작성** — `funnel.js`를 복사해 exec 함수(API 호출)만 교체, 또는 `member/crew/board`식 단순 arrival
> ③ **시드 준비** — C절 공통 시드 + 이 시나리오 전용 데이터의 DB/SQL 초안
> ④ **결과 해석** — 단계별 수치로 병목(CPU / hikari / 외부 호출) 분리 분석"

규칙:
- 사용자의 답을 받은 뒤 H절 템플릿을 채운다. **공통 틀(B~G)은 그대로 재사용**하고, 대상·시드·판정 기준만 시나리오에 맞게 바꾼다.
- 운영(team05)에 닿는 명령은 **무엇을·언제·어느 규모로** 돌릴지 먼저 보고하고 사용자 go를 받은 뒤 실행한다. 공용 서버라 밤/한가할 때.
- 비밀번호·토큰·자격증명은 지어내거나 채팅에 쓰지 않는다. 근거 없는 수치는 "확인 못 함"이라고 쓴다.
- RPS(요청/초)와 TPS(완결 거래/초)를 섞지 말고 구분해 보고한다.
