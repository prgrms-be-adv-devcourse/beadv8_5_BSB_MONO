# 부하 테스트 수집 자료 (2026-11-19, main 68f0336)

team05(운영 dev 서버)에 넣은 예매 부하의 원본 자료다.
사람과 AI가 이 폴더만 읽고 "무엇을, 어떻게 넣었고, 무엇이 나왔는지"를 다시 계산할 수 있게 정리했다.

> **읽는 AI에게.** 먼저 이 파일을 끝까지 읽고, 그다음 볼 실행 폴더의 `MANIFEST.md`를 읽는다.
> 수치를 인용할 때는 어느 실행(폴더)·어느 단계인지와 그 실행의 조건을 함께 말한다.
> 실행마다 조건이 달라서, 조건을 빼고 숫자만 비교하면 틀린 결론이 나온다(아래 「비교할 때 주의」).
> 이 파일에 없는 내용은 지어내지 말고 "기록 없음"이라고 답한다.

## 1. 대상 시스템

- 서버: team05, AWS t3.large (2 vCPU, 메모리 7.6GB, 스왑 3GB), k3s, 서비스마다 파드 1개. 주소 `https://crewrun.duckdns.org`. 실사용자는 없다.

## 2. 예매 흐름과 호출하는 API

한 사람이 예매할 때 서버에 보내는 요청이다. 두 스크립트 모두 이 흐름을 쓴다.

| 순서 | 요청 | 구분(`kind`) | 설명 |
|---|---|---|---|
| 1 | `GET /api/v1/product/races/{raceId}` | read | 대회 상세 조회 |
| 2 | `POST /api/v1/queue` | queue | 대기열에 줄 서기 (이미 줄에 있으면 409) |
| 3 | `GET /api/v1/queue/races/{raceId}/racecourses/{raceCourseId}` | queue | 내 순번 조회. 3초마다 반복. `data.canEnter`가 true면 입장 가능 |
| 4 | `GET /api/v1/order/queue/admission` | queue | 입장 허가 확인 |
| 5 | `POST /api/v1/order/participations` | write | 참가 신청서 저장 (201) |
| 6 | `POST /api/v1/order/orders` | write | 주문 생성. 상품 서비스에 자리 확보를 요청한다 (201, 자리 없으면 409, 내부 오류면 503) |
| 7 | `POST /api/v1/order/orders/{orderId}/payment` | write | 예치금 결제 (200 결제 완료, 202 결제 확인 중) |

알아 둘 서버 동작:
- **대기열은 5초마다 20명, 즉 초당 4명만 입장시킨다**(`queue.schedule.size: 20`, `time: 5000`). 그래서 결제까지 가는 속도는 초당 약 4건을 넘지 못한다.
- **신청은 한 회원이 대회당 한 번만 할 수 있다.** 두 번째부터는 409(`ORDER_DUPLICATE_PARTICIPATION`)다. 그래서 실행마다 새 대회를 만든다.
- 결제는 구매자 지갑과 **플랫폼 전체에 하나뿐인 보관 지갑**을 함께 잠근다(`CashSupport.lockCustomerAndHoldingWallets`).
- nginx는 `/api/v1/auth/` 요청만 IP당 초당 1건으로 제한한다. 예매 경로에는 제한이 없다.

## 3. 스크립트 두 개 (부하를 넣은 방식)

스크립트는 `../k6/`에 있다. 통과 기준은 같다: 조회 p95 300ms, 대기열 p95 200ms, 쓰기 p95 1초, 실패율 1% 미만.
자동 중단: 전체 실패율 5%(30초 뒤부터), 쓰기 p99 5초(2분 뒤부터).

### 3-1. 기준선: 최악 가정 — `funnel.js`

**대기자와 구매자가 다른 사람이다.** 세 흐름을 동시에 돌린다.

| 시간(초) | 흐름 | 하는 일 |
|---|---|---|
| 0~30 | 입장(`enter`) | 대기자가 대회 상세 조회 → 2초 뒤 **대기용 대회**에 줄 서기 |
| 33~213 | 순번 조회(`poll`) | 대기자가 3초마다 순번 조회. **입장하지 않는다. 줄이 줄어들지 않는다** |
| 33~153 | 구매(`buy`) | 구매자가 **구매용 대회**에 줄 서기 → 입장 → 30초 뒤 신청 → 주문 → 10초 뒤 결제. 도착이 끝난 뒤 최대 90초 더 기다린다 |

- 도착률을 고정한다(k6 `constant-arrival-rate`). 서버가 느려져도 같은 속도로 요청이 들어오고, 보내지 못한 요청은 `dropped_iterations`로 센다.
- 순번 조회 건/초 = 대기자 수 ÷ 3초.
- 처음 20초(결제 몰림은 10초)는 워밍업으로 표시해 통과 기준에서 뺀다(`phase` 태그).

| 단계 | 대기자 | 순번 조회 | 구매 도착 |
|---|---|---|---|
| `s1` | 300명 (10명/초 × 30초) | 100건/초 | 2건/초 × 120초 = 240명 |
| `s2` | 600명 | 200건/초 | 3건/초 × 120초 = 360명 |
| `s3` | 990명 | 330건/초 | 2건/초 × 120초 = 240명 |
| `buystress`(결제 몰림) | 400명 (20명/초 × 20초) | 133건/초 × 60초 | 15건/초 × 60초 = 900명 |

이 스크립트가 재는 것: "줄 선 사람이 한 명도 빠지지 않고 계속 순번만 조회하는" 최악의 경우에 서버가 버티는지.

### 3-2. 실제 흐름: 오픈 몰림 — `rush.js`

**대기자와 구매자가 같은 사람이다.** 흐름은 하나다.

1. N명이 30초에 걸쳐 고르게 도착한다(k6 `per-vu-iterations`, 한 사람 = VU 하나, 한 번만 돈다).
2. 대회 상세 조회 → 2초 뒤 **한 대회**에 줄 서기.
3. 3초마다 순번을 조회한다. 줄에 없다고 나오면(404) 다시 줄을 선다.
4. 입장하면 30초 뒤 신청 → 주문 → 10초 뒤 결제.

- 길이를 정하지 않는다. 줄이 다 빠질 때까지 돈다(N ÷ 4초 + 마지막 사람의 구매 약 40초).
- 순번 조회는 처음에 가장 많고(N ÷ 3건/초), 줄이 빠지면서 줄어든다.
- 워밍업 구간이 없다. 전 구간이 통과 기준에 들어간다.
- 단계: `r300`(300명), `r600`(600명), `r990`(990명). `r30`은 흐름 확인용이다.

이 스크립트가 재는 것: 예매 오픈 직후 N명이 몰렸을 때의 실제 모습.

### 3-3. 가정으로 정한 값 (측정해서 정한 값이 아니다)

도착 30초, 신청서 작성 30초, 결제 확인 10초, 순번 조회 180초·구매 도착 120초·추가 대기 90초(기준선).
순번 조회 3초는 화면의 실제 폴링 주기다.

| `<단계>.json` | k6 요약(`--summary-export`). `metrics`에 지표별 avg·p(90)·p(95), `root_group.checks`에 확인 항목별 통과·실패 건수 |
| `<단계>-raw.csv.gz` | 요청 하나하나의 원시 기록(gzip). 아래 「원시 CSV」 |
| `<단계>.tps.json` | 원시 CSV에서 계산한 처리량과 엔드포인트별 지연(`../k6/analyze.py`) |
| `<단계>.prom.json` | 실행 시간창의 서버 지표 시계열(`../k6/promrange.py`, Prometheus) |

### 원시 CSV (`<단계>-raw.csv.gz`)

k6의 `--out csv` 형식이다. 한 줄이 측정값 하나다.
열: `metric_name, timestamp(초, epoch), metric_value, check, error, error_code, expected_response, group, method, name, proto, scenario, service, status, subproto, tls_version, url, extra_tags, metadata`

- 요청 지연은 `metric_name = http_req_duration`인 줄의 `metric_value`(ms)다. `name`이 엔드포인트, `status`가 응답 코드, `expected_response`가 기대한 응답이었는지다.
- `extra_tags`에 `kind=read|queue|write`와 (기준선만) `phase=warmup|main`이 들어 있다.
- `scenario`는 `enter`·`poll`·`buy`(기준선) 또는 `rush`(실제 흐름)다.
- 사용자 흐름 하나가 끝나면 `iteration_duration` 줄이 하나 생긴다.

### `<단계>.tps.json`

- `rps_avg`, `rps_peak`: 초당 보낸 요청 수(평균, 최대). `ok_rps_*`: 기대한 응답을 받은 요청만.
- `tps_by_scenario`: 흐름별로 끝난 건수(`completed`)와 초당 끝난 건수.
- `per_second`: 1초 단위 배열(`rps`, `ok_rps`, `tps_<흐름>`, `tps_total`). 첫 원소가 `window_epoch[0]` 시각이다.
- `endpoints`: 엔드포인트별 `count`, `failed`, `avg_ms`, `p50_ms`, `p95_ms`, `p99_ms`, `max_ms`, `status`(응답 코드별 건수).
- 용어: **RPS**는 요청 수/초, **TPS**는 끝난 사용자 흐름 수/초다. 결제 처리율은 `endpoints`의 결제 엔드포인트 `status["200"]` ÷ 구간 길이로 구한다.

### `<단계>.prom.json`

`series.<이름>`이 Prometheus 응답 그대로다(`metric` 라벨 + `values: [[시각, "값"], …]`, 15초 간격).

| 이름 | 뜻 |
|---|---|
| `node_cpu_pct` | 노드 CPU 사용률(%). **`1119-pm-…`에서는 1분 평균, 그 뒤 실행에서는 15초 단위다** |
| `node_cpu_pct_1m` | 1분 평균(`1119-rush-…`, `1119-eve-…`에만 있다). 실행끼리 비교할 때 쓴다 |
| `node_cpu_iowait_pct`, `node_load1`, `node_mem_avail_mb`, `node_swap_used_mb` | 노드 I/O 대기, load, 가용 메모리, 스왑 사용량 |
| `pod_cpu_cores`, `pod_cpu_cores_1m` | 파드별 CPU(코어, 2코어 중). 15초 단위와 1분 평균 |
| `pod_mem_ws_mb` | 파드별 메모리(working set) |
| `hikari_pending`, `hikari_active` | 서비스별 DB 커넥션 대기 수, 사용 중 수 |
| `heap_pct`, `gc_pause_s_per_s`, `jvm_threads_live` | 서비스별 힙 사용률, GC 멈춤 시간, 스레드 수 |
| `server_rps_by_app`, `server_5xx_rps_by_app`, `server_p95_s_by_app` | 서버가 직접 잰 서비스별 요청 수/초, 5xx/초, p95(초) |
| `gateway_rps` | 게이트웨이가 처리한 요청 수/초 |

## 7. 비교할 때 주의

- **스크립트가 다르면 단계끼리 직접 비교하지 않는다.** `funnel.js`와 `rush.js`는 요청 구성과 지속 시간이 다르다. 잇고 싶으면 "초당 요청 수 대비 CPU·지연"으로 본다.
- **같은 조건에서 다시 재도 값이 달라졌다.** 기준선 s1의 CPU가 오후 59%, 저녁 44%였다. 원인은 확정하지 못했다(단계 사이 쉼 여부, 공용 서버의 다른 부하, 로그인 직후 여부). 한 번 잰 값으로 단정하지 않는다.
- `1119-pm-…`의 `node_cpu_pct`는 1분 평균이고, 그 뒤 실행은 15초 단위다. 비교는 1분 평균끼리 한다.
- `1119-am-…`의 쓰기 수치와, 그 실행에서 낸 "보관 지갑 잠금은 병목이 아니다"라는 결론은 무효다. 결제 요청이 서버에 닿지 않았다.
- 보관 지갑 잠금의 한계는 측정하지 못했다. 대기열이 결제 유입을 초당 약 4건으로 묶기 때문이다.
- 실패율 0%만 보고 통과로 판단하지 않는다. `root_group.checks`에서 `신청 201`·`주문 201/200`·`결제 200(PAID)/202(PAYING)` 건수가 0이 아닌지 본다.
- 운영 DB에는 판매자용 부하 계정(`loadtest1000`, `product_seller` id 900001)과 이 측정으로 만든 테스트 대회(56~85번)가 남아 있다.
