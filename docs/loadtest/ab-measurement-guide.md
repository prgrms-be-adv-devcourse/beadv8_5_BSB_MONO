# A·B 부하 측정 따라 하기

내 서비스 코드를 고친 뒤 정말 나아졌는지를 숫자로 보여 주는 방법이에요.
GitHub 실행 머신 안에서 내 서비스와 DB 등을 자원을 묶은 컨테이너로 띄우고, **고치기 전 코드(A)**와 **고친 코드(B)**를 같은 머신에서 번갈아 3번씩 재요.
운영·dev 서버에는 요청이 가지 않아요.

예치금 측정(`docs/loadtest/scenario-b/`)과 주문 결제 잠금 측정(`docs/measurements/load/`)이 이미 이 방식이에요. 두 폴더를 복사해서 내 서비스에 맞게 바꾸면 돼요.

## 어떻게 도나

1. PR에 라벨을 붙여요(또는 Actions에서 직접 실행).
2. 이미지 두 개를 빌드해요. B = PR 커밋, A = B에서 고친 커밋만 되돌린 코드예요.
3. 한 머신에서 A 1회 → B 1회 → A 2회 → B 2회 → A 3회 → B 3회 순서로 재요.
   - 한 회차 = 빈 DB로 띄우기 → 시드 → 시나리오마다 k6 → 정확성 SQL → 지표·그래프 저장 → 내리기
4. 3회 중 가운데 값으로 판정해 실행 화면 Summary에 써요.
5. 원본은 아티팩트로 30일 보관해요.

A·B를 번갈아 재는 이유: 공용 실행 머신은 실행마다 조금씩 빠르기가 달라요. 같은 머신에서 번갈아 재면 그 흔들림이 A와 B에 고르게 나뉘어, 남는 차이는 고친 코드 때문이라고 말할 수 있어요.

## 언제 쓰나

**맞는 경우**

- 코드를 고친 뒤 「응답이 빨라졌다」「SQL이 줄었다」를 전후 숫자로 보여 줄 때
- 잠금·동시 요청처럼 몰릴 때만 드러나는 문제를 재현할 때
- 바깥 서비스(PG, Redis, DB)가 느려질 때 내 서비스가 버티는지 볼 때
- 동시에 몰려도 데이터가 맞는지(중복, 초과 판매 등) 확인할 때

**안 맞는 경우**

- 「운영에서 초당 몇 건까지 버티나」 같은 실제 한계: 자원을 일부러 묶어서 숫자가 운영과 달라요. 운영 측정(`docs/loadtest/main_scenario/`)이 맞아요
- 게이트웨이부터 여러 서비스를 거치는 전체 흐름: 한두 서비스만 띄워요
- 몇 시간씩 돌려야 보이는 문제: 한 실행은 최대 350분이에요

## 무엇을 복사하나

예치금 측정 기준으로 적었어요. 주문 측정은 같은 역할의 파일이 `docs/measurements/load/`에 한 폴더로 모여 있어서, 처음 만들 때는 그쪽이 더 단순해요.

| 파일 (예치금) | 하는 일 | 내 서비스에 맞게 바꿀 것 |
|---|---|---|
| `.github/workflows/cash-load-test.yml` | 라벨을 보고 A·B 이미지를 만들고, 번갈아 돌리고, 결과를 아티팩트로 올려요 | 워크플로 이름, 라벨 이름, 빌드할 모듈(`MODULE=cash-service`), `concurrency` 그룹 이름 |
| `container/compose.load.yml` | 내 서비스 + MySQL·Kafka·Redis·Prometheus를 자원을 묶어 띄워요 | 내 서비스 컨테이너와 필요한 인프라, CPU·메모리 제한, 측정용 환경 변수 |
| `container/run.sh` | 한 회차: 빈 DB로 띄우기 → 시드 → 시나리오마다 k6 → 정확성 확인 → 지표 저장 → 내리기 | 시나리오 목록, 시드 순서, 확인 SQL 호출 |
| `b*.js` (k6 스크립트) | 시나리오마다 요청을 보내요. 태그(`api`, `stage`)를 붙여 API·단계별로 나눠 봐요 | 내 API 주소와 요청 모양, 부하 크기 |
| `sql/01-seed.sql`, `seed-*.sh` | 시나리오에 필요한 회원·데이터를 넣어요 | 내 서비스 테이블에 맞는 시드 |
| `verify.sh`, `sql/10-verify.sql`, `sql/12-verify-charge.sql` | 시나리오가 끝날 때마다 데이터가 맞는지 SQL로 확인해요 (예치금은 돈, 주문은 판매 수) | 내 서비스에서 「절대 틀리면 안 되는 것」을 0건 확인 SQL로 |
| `container/report.py` | 3회 결과를 모아 가운데 값 표와 판정을 Summary에 써요 | 내 판정 기준 번호와 읽을 지표 |
| `container/ab-fixes.txt` | A를 만들 때 B에서 되돌릴 「고친 커밋」 목록이에요 | 내가 고친 커밋 (최근 것부터) |
| `docs/measurements/…-판정기준.md` | 무엇을 왜 재고 어떤 숫자면 문제인지, **재기 전에** 커밋해 두는 문서예요 | 새로 써요 (아래 「판정 기준 쓰는 법」) |

앞에 경로가 없는 파일은 `docs/loadtest/scenario-b/` 아래에 있어요.

바깥 서비스는 가짜로 둬요. 예치금은 PG·은행을 가짜로 두고, 응답 지연을 설정으로 넣어요(`application.yaml`의 `fake-confirm-delay`). 주문 측정은 예치금 앞에 Toxiproxy(앱과 대상 사이에 끼워 지연을 넣는 중계기)를 둬요.

## 만드는 순서

1. **판정 기준 문서부터 써요.** 코드에서 의심한 곳, 그걸 건드리는 시나리오, 문제로 볼 숫자를 정하고 커밋해요.
2. **compose 파일로 내 서비스를 띄워요.** 자원 제한을 걸고, 바깥 서비스는 가짜로 바꿔요.
3. **시드와 k6 스크립트를 써요.** 시나리오 하나부터 시작해요.
4. **정확성 확인 SQL을 써요.** 몰려도 틀리면 안 되는 것(중복 처리, 초과 판매, 합계)을 0건으로 확인해요.
5. **맥에서 짧게 한 바퀴 돌려 봐요.** 도는지만 확인해요. 이 숫자로는 판정하지 않아요.
6. **워크플로를 만들고 PR에 라벨을 붙여요.** 먼저 지금 코드(A)만 3번 재서 문제가 있는지 봐요.
7. **고친 뒤 `ab-fixes.txt`에 고친 커밋을 적고 A·B 라벨을 붙여요.**
8. **결과 문서를 써요.** 기준대로 판정하고, 기준을 못 넘은 것도 그대로 적어요.

5번 예시 (예치금, `backend/`에서):

```bash
QUICK=1 OUT=/tmp/cashload loadtest/scenario-b/container/run.sh
```

## 판정 기준 쓰는 법

숫자를 본 뒤 기준을 바꾸지 않으려고, 재기 전에 문서로 커밋해요. 예치금은 세 종류로 나눴어요(`docs/measurements/2026-11-16-예치금-부하-판정기준.md`).

| 종류 | 뜻 | 예 (예치금) |
|---|---|---|
| 문제 있음 (P) | 지금 코드(A)가 이 선을 넘으면 고칠 대상이에요 | 결제 동시 4개에서 p99가 1초 이상 |
| 나아짐 (G) | 고친 코드(B)가 이 조건을 모두 맞추면 나아졌다고 해요 | 고친 문제의 P가 더는 맞지 않음, 고치지 않은 곳이 20% 넘게 나빠지지 않음 |
| 정확성 (C) | A·B 모든 회차에서 0이어야 해요. 하나라도 틀리면 가장 먼저 고쳐요 | 중복 원장 0건, 잔액 어긋남 0원 |

- 값마다 근거를 적어요. 근거가 없으면 「추천값(미확정)」, 자료가 없어 정한 값이면 「가정」이라고 붙여요. 예: 주문이 예치금을 2초까지 기다리니 그 절반인 1초.
- 값은 3회 중 가운데 값으로 판정해요. 정확성만은 3회 모두 통과해야 해요.
- A도 같은 기준으로 봐요. A가 예전 측정처럼 기준을 넘지 않으면 그 실행의 머신이 달랐다는 뜻이라, B만 보고 나아졌다고 말하지 않아요.
- 기준을 못 넘은 항목도 지우지 않고 「나아지지 않음」으로 적어요.

## 돌리고 결과 받기

**PR에 라벨 붙이기.** 붙이는 순간의 PR 맨 끝 커밋으로 돌아요. 워크플로 파일도 그 PR 것을 써서 머지 전에도 돼요. 다시 돌리려면 라벨을 뗐다 다시 붙여요.

```bash
gh pr edit <PR번호> --add-label cash-load-test-ab
```

**Actions에서 직접 실행.** 워크플로가 기본 브랜치에 들어간 뒤에는 Actions → 워크플로 → Run workflow로도 돌려요. 비교할 두 커밋(`ref_a`, `ref_b`), 반복 횟수, 시나리오를 넣을 수 있어요.

**결과 받기.**

```bash
gh run list --workflow cash-load-test.yml --limit 5
```

```bash
gh run download <실행 번호> -n cash-load-results -D <받을 폴더>
```

- 실행 화면의 Summary에 가운데 값 표와 판정이 나와요.
- 아티팩트에는 회차마다 k6 요약, 정확성 SQL 결과, 그래프, JFR·GC 로그, Prometheus 데이터가 있어요. 30일 뒤 지워지니 필요한 건 받아 둬요.
- 받기는 레포 폴더 안에서 해야 돼요(`gh`가 레포를 알아야 해요). 라벨을 붙이려면 레포 쓰기 권한이 필요해요.

## 주의할 점

- **숫자는 운영 성능이 아니에요.** 자원을 묶은 컨테이너에서 잰 「같은 조건에서의 전후 비교」예요.
- **서로 다른 실행의 숫자는 비교하지 않아요.** 실행마다 머신이 흔들려요. 같은 실행 안의 A·B만 비교해요.
- **자원 제한은 「이 이상 못 쓴다」는 천장이에요.** 메모리 제한은 어디서나 거의 같지만, CPU 제한은 머신이 바쁘면 덜 받아요. 응답 시간을 재는 측정은 그만큼 흔들려요.
- **막 띄운 직후는 느려요.** 처음 도는 코드는 JVM이 클래스를 읽고 컴파일해요. 시나리오 앞에 예열(짧게 돌리고 버림)을 둬요.
- **한 실행은 최대 350분이에요.** A·B 3번이면 한 바퀴를 50분 안쪽으로 맞춰요.
- **워크플로마다 `concurrency` 그룹을 둬요.** 같은 측정끼리 동시에 돌지 않게 해요(예치금 `cash-load-test`, 주문 `order-load-test`).
