# 완성품 API 게이트웨이 vs Spring Cloud Gateway

> Spring Cloud Gateway도 보통 Docker 컨테이너로 띄운다. 그래서 진짜 차이는 "Docker냐 Spring이냐"가 아니다.
> **이미 만들어진 게이트웨이 제품을 설정만 해서 쓰느냐, 내가 코드로 게이트웨이 앱을 만드느냐**의 차이다.

- **완성품 게이트웨이**: Nginx, Kong, Traefik, Envoy, APISIX 등. 이미지 받아서 설정 파일(YAML, conf)로 동작을 정한다.
- **직접 만드는 게이트웨이**: Spring Cloud Gateway. Spring Boot 앱을 하나 만들고 라우팅·필터를 Java/Kotlin 코드나 `application.yml`로 정의한다.

## 한눈에 비교

| | 완성품 (Nginx, Kong, Traefik 등) | Spring Cloud Gateway |
|---|---|---|
| 동작 방식 | 설정 파일로 정함 | 코드 + 설정으로 정함 |
| 만든 언어 | C, Go, Lua 등 | Java (JVM) |
| 성능·자원 | 가볍고 빠름, 메모리 적게 씀 | JVM이라 메모리를 더 쓰고 시작이 느림 |
| 맞춤 로직 | 플러그인 범위 안에서만 가능하고, 복잡하면 Lua 같은 걸 써야 함 | Java 코드로 자유롭게 짤 수 있음 |
| 스프링 생태계 연동 | 따로 붙여야 함 | Eureka(서비스 찾기), Spring Security, Resilience4j(장애 차단) 등과 바로 붙음 |
| 관리 주체 | 주로 인프라/DevOps 쪽 | 주로 백엔드 개발자 |
| 배포 | 설정만 바꾸면 반영(핫 리로드되는 것도 많음) | 코드를 바꾸면 다시 빌드하고 배포 |

## 각각 언제 잘 맞나

### 완성품이 잘 맞는 경우

- 라우팅, SSL 처리, 요청 수 제한, 로드밸런싱처럼 **흔한 기능만** 필요할 때
- 서비스들이 여러 언어로 섞여 있을 때 (Node, Go, Spring 등)
- 트래픽이 많아서 성능과 자원이 중요할 때
- Traefik처럼 Docker/K8s 라벨만 읽고 라우팅을 자동으로 잡아주는 편리함이 필요할 때

### Spring Cloud Gateway가 잘 맞는 경우

- 백엔드가 거의 다 스프링이고, 팀이 Java에 익숙할 때
- **업무 로직이 섞인 처리**가 필요할 때. 예를 들어 JWT를 까서 사용자 등급에 따라 다른 서비스로 보내거나, DB나 Redis를 확인한 뒤 막는 경우
- Eureka 같은 스프링 기반 서비스 찾기와 엮어서 `lb://user-service`처럼 쓰고 싶을 때
- 게이트웨이 동작을 일반 코드처럼 테스트하고 리뷰하고 싶을 때

## 실무에서 자주 보는 구성

둘 중 하나만 고르는 대신 **겹쳐서 쓰는 경우가 많다.**

```
클라이언트 → Nginx/Traefik (SSL, 정적 파일, 1차 관문)
          → Spring Cloud Gateway (인증, 업무 로직 라우팅)
          → 각 마이크로서비스
```

앞단은 가볍고 빠른 프록시에 맡기고, 뒷단은 스프링 쪽 로직이 필요한 부분만 처리하는 식이다.

## 정리

- 흔한 기능만 필요하고 성능이 중요하면 → **완성품 게이트웨이**
- 스프링 위주인 팀이 게이트웨이에서 직접 로직을 짜야 하면 → **Spring Cloud Gateway**
