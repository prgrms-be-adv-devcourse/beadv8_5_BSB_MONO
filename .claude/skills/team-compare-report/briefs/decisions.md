# 설계 선택 조사 지시서

팀 저장소에서 설계 선택 8가지를 조사합니다. 선택마다 「고민한 선택지 → 고른 것 → 이유」를 글로 남은 근거에서만 찾습니다. 보고는 한국어 존댓말로 합니다.

- 선택 지점과 선택지: `<스킬 폴더>/decisions-topics.json`
- 대상 코드 폴더, GitHub 저장소 이름, 결과 파일 경로는 지시 메시지에 있습니다.
- PR은 `gh pr list -R prgrms-be-adv-devcourse/<저장소> --state all --search "키워드" --json number,title,body`, `gh pr view N -R ... --json body,comments,reviews`로 읽습니다. 주제마다 한국어·영어 키워드를 여러 개 씁니다(예: outbox 아웃박스, lock 락 동시성, idempotency 멱등, gateway 게이트웨이, kafka, feign, deploy 배포, k8s).
- 저장소 안의 docs·README·ADR·코드 주석도 봅니다.

## 규칙
- choice(고른 것): 코드로 확인합니다. options 중 하나를 그대로 씁니다. 맞는 것이 없으면 짧은 이름을 새로 씁니다. 서비스마다 다르면 「섞어 씀」입니다.
- considered(고민한 선택지): 「A와 B를 비교했다」, 「A 대신 B」처럼 글로 실제로 적힌 선택지만 넣고, 고른 것도 포함합니다. 작업 설명이나 계획 문장은 비교가 아닙니다. 그 주제와 다른 대상(예: 다른 테이블의 락)을 비교한 글도 넣지 않습니다. 없으면 빈 배열입니다.
- why(이유): 글로 남은 이유를 한 문장, 70자 이내, 합니다체로 씁니다. 「무엇이 문제 → 그래서 이것을 골랐다」 순서입니다. 근거가 없으면 why와 src를 비웁니다. 코드를 보고 이유를 추측하지 않습니다.
- src(출처): 「PR #123」, 「docs/xxx.md」, 「Xxx.java 주석」처럼 씁니다. 신뢰 순서는 설계 문서 → PR 본문·리뷰 → 코드 주석입니다. 자동 리뷰 봇의 글은 출처로 쓰지 않습니다.
- ev: choice를 확인한 코드 경로:줄 하나입니다.
- 대상 파일 수정 금지, 빌드·테스트 금지. 줄표(—)와 번역체 금지, 상태값 영어·코드 이름 대신 뜻으로 씁니다.

## 출력
```json
{"decisions": {"event": {"choice": "…", "considered": [], "why": "", "src": "", "ev": "경로:줄"}}}
```
8개 주제를 모두 씁니다. 마지막 답에는 주제마다 「고른 것 · 고민한 선택지 수 · 이유 출처 유무」 한 줄씩만 적습니다.
