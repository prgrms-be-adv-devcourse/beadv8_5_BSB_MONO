# 팀 비교 리포트

대상: $ARGUMENTS

결과물은 항상 같은 모양의 artifact 한 페이지입니다. 사이드바에 **한눈에 보기 → (항목별 판정) → 우리 팀 적용안 → 팀별 상세**가 있습니다.
모양은 [`template.html`](template.html)이 정하고, 이 스킬은 내용만 [`data-schema.md`](data-schema.md) 형식의 JSON으로 채웁니다. 실제로 채운 예는 [`example.json`](example.json)(8기 인프라 비교)입니다.

## 1. 범위 정하기

1. 주제와 기수를 정합니다. 인자에 없으면 묻습니다.
2. 팀 저장소를 찾습니다: `gh repo list prgrms-be-adv-devcourse --limit 200 --json name,description`. 설명의 「N기 M팀」으로 팀 번호를 맞춥니다. 저장소 이름의 숫자와 팀 번호가 다를 수 있습니다(예: 3팀 저장소가 `beadv8_8_AHJB_BE`).
3. 우리 팀은 이 레포입니다. 몇 팀인지는 `git remote -v`의 저장소 이름으로 확인합니다.

완료 기준: 팀 번호 · 팀 이름 · 백엔드 저장소 · (주제에 필요하면) 프론트 저장소 목록이 모든 팀에 대해 있습니다.

## 2. 점검표 만들기

주제를 5~10개 항목으로 나누고, 항목마다 「잘함」의 기준을 한 줄로 적습니다. 예: 인프라는 서비스 구조·서버·배포·데이터·모니터링·보안, 회원은 테이블·트랜잭션·이벤트·인증·탈퇴·중복 가입.
사용자가 항목을 주지 않았으면 초안을 보여 주고 확인받은 뒤 조사를 시작합니다.

완료 기준: 모든 팀을 같은 점검표로 판정할 수 있습니다.

## 3. 팀별 조사

1. 저장소를 scratchpad에 얕게 내려받습니다: `git clone --depth 1 <url>`. 기본 브랜치(dev·develop)를 보고, 브랜치와 커밋을 팀의 `source`에 적습니다.
2. 점검표 항목마다 판정(`good`·`ok`·`weak`·`none`·`unknown`)과 근거 파일을 남깁니다. 저장소에서 찾지 못한 것은 「없음」이 아니라 「확인 못 함」입니다.
3. 팀이 많으면 팀마다 서브에이전트에 나눠 맡겨도 됩니다. 읽기만 하고 빌드·테스트는 돌리지 않게 합니다. 브리프에 점검표와 이 단계의 규칙, 그리고 아래 「글 쓰는 법」을 그대로 넣습니다.

완료 기준: 모든 팀의 모든 점검표 항목에 판정과 근거 파일이 있습니다.

## 4. 핵심 주장 다시 확인

리포트에서 눈에 띌 주장은 코드를 직접 열어 한 번 더 확인합니다. 다른 팀의 「아쉬운 점」, 우리 팀의 모든 판정, 적용안의 근거가 여기에 해당합니다.
확인이 안 되는 주장은 빼거나 「확인 필요」를 붙입니다. 서버 설정(.env)이나 콘솔에서 만든 자원처럼 저장소에 없는 것은 `footer`에 「보지 않음」으로 적습니다.

완료 기준: 리포트의 모든 「아쉬운 점」과 적용안 근거가 코드로 확인됐거나 「확인 필요」로 표시되어 있습니다.

## 5. 우리 팀 적용안

다른 팀이 잘한 것 중 우리 팀에 없는 것을 고릅니다. 작고 급한 것부터 순서를 매기고, 항목마다 참고할 팀과 크기(작음·중간·큼) 또는 종류(보안·돈)를 붙입니다. 데이터가 사라지거나 돈·보안에 걸린 항목은 `urgent`로 맨 앞에 둡니다.

완료 기준: 적용안의 모든 항목에 「무엇이 문제 → 고치면 어떻게 되는지」, 참고 팀, 크기가 있습니다.

## 6. 만들고 띄우기

1. `data.json`을 scratchpad에 씁니다.
2. 검사하고 HTML로 만듭니다: `python3 .claude/skills/team-compare-report/build.py <data.json> <scratchpad>/<주제>-report.html`. 오류나 경고가 나오면 JSON을 고쳐 다시 돌립니다. `template.html`은 고치지 않습니다. 모양을 바꾸려면 `template.html`을 고치는 별도 작업으로 합니다.
3. Artifact 도구로 그 HTML을 게시합니다. 같은 리포트를 고칠 때는 같은 파일 경로로 다시 게시해 주소를 유지합니다.

완료 기준: build.py가 경고 없이 「만듦」을 출력했고, artifact 링크가 있습니다.

## 글 쓰는 법

JSON을 쓰는 처음부터 이 규칙대로 씁니다. 다 쓴 뒤 줄이는 방식으로 하지 않습니다. 서브에이전트에 조사를 맡길 때도 이 절을 브리프에 그대로 넣습니다.

### 분량

리포트에는 판정과 근거만 둡니다. 배경 설명, 들어가는 말, 정리하는 말은 쓰지 않습니다.

| 자리 | 한도 |
|---|---|
| `summary` | 3줄, 줄마다 45자 이내 |
| `good` · `bad` · `take` 항목 | 항목마다 한 줄, 40자 이내 |
| `facts` 값 | 40자 이내. 기술 이름 나열은 「·」로 |
| `checks[].text` | 두 문장 이내 |
| 적용안 `why` | 한 문장. 「문제 → 고치면 어떻게 되는지」 |
| `footer` | 한 줄. 조사 방법과 보지 않은 범위만 |

한도를 넘으면 문장을 줄이지 말고 내용을 덜어냅니다. 꼭 남겨야 하면 항목을 둘로 나눕니다.

### 줄바꿈

- 한 항목에는 한 가지만 씁니다. 「~하고, ~하며」로 두 사실을 잇지 말고 항목을 나눕니다.
- 셋 이상 나열하면 쉼표 대신 「·」로 잇습니다. 예: `PostgreSQL · Redis · Kafka`
- 괄호 보충은 항목마다 한 번까지만 씁니다.
- 숫자와 단위, 도구 이름은 붙여 써서 줄이 중간에 끊기지 않게 합니다. 예: `t3.medium`, `10초`

### 자연스러운 한국어

팀원에게 말로 설명하듯 씁니다. 처음 보는 사람이 다시 해석하지 않아도 읽혀야 합니다.

- 상태값 영어와 코드 이름은 뜻으로 씁니다. 도구 이름(Prometheus, k3s)은 그대로 씁니다.
- 우리끼리 만든 말, 비유, 줄표(—), 쌍점 뒤에 결론을 붙이는 문장은 쓰지 않습니다.
- 문장은 합니다체, 목록은 명사형(「~함」, 「~ 없음」)으로 끝냅니다.
- 아래 왼쪽 말이 보이면 오른쪽처럼 고칩니다.

| 이렇게 쓰지 않음 | 이렇게 씀 |
|---|---|
| 짚는다 · 짚어 본다 | 확인한다 |
| 끌어낸다 · 이끌어 낸다 | 만든다 · 얻는다 |
| ~를 겪는다 | ~가 불편하다 · ~가 생긴다 |
| ~를 통해 | ~로 |
| ~에 대해 | ~를 |
| ~하는 것이 중요합니다 · 필요합니다 | ~해야 합니다 |
| 효과적으로 · 다양한 · 핵심적인 | 빼거나 구체적인 숫자·이름으로 |
| 활용한다 | 쓴다 |
| 진행한다 | 한다 |
| 가능하다 · 가능해진다 | ~할 수 있다 |
| 존재한다 | 있다 |

`build.py`는 위 한도와 왼쪽 말을 찾아 경고를 출력합니다. 경고가 나오면 그 항목을 고쳐 경고가 없어질 때까지 다시 돌립니다.
