# 데이터 형식

`template.html`의 `/*DATA*/null` 자리에 들어가는 JSON입니다. 실제로 채운 예는 [`example.json`](example.json)(8기 인프라 비교)입니다.

글자 칸(문자열)에는 `**굵게**`와 `` `코드` ``만 쓸 수 있습니다. HTML 태그는 글자로 보입니다.

## 맨 위

| 키 | 필수 | 뜻 |
|---|---|---|
| `title` | 예 | 페이지 이름. 「8기 인프라 비교」처럼 짧은 명사구 |
| `subtitle` | 예 | 조사 범위와 기준일. 예: `8기 1~8팀 백엔드 저장소 기준 · 2026-11-12 조사` |
| `navCaption` | 아니요 | 사이드바 제목 아래 작은 글. 예: `1~8팀 · 11/12` |
| `summary` | 예 | 한눈에 보기 맨 위 결론 2~3줄. 첫 줄이 가장 중요한 결론 |
| `kindLabel` | 아니요 | 한눈에 표에 「방식」 열을 넣을 때 열 이름. 없으면 열을 뺍니다 |
| `footer` | 예 | 조사 방법과 확인하지 못한 범위 한 줄 |
| `teams` | 예 | 팀 목록. 아래 「팀」 |
| `matrix` | 아니요 | 항목별 판정표. 넣으면 「항목별 판정」 페이지가 생깁니다 |
| `apply` | 예 | 우리 팀 적용안. 아래 「적용안」 |

## 팀 (`teams[]`)

| 키 | 필수 | 뜻 |
|---|---|---|
| `id` | 예 | 페이지 주소. `team1`처럼 영문·숫자만 |
| `no` | 예 | 팀 번호(숫자) |
| `name` | 예 | 팀 이름. 우리 팀은 `크루런 (우리)` |
| `product` | 예 | 서비스 이름이나 저장소 이름 |
| `ours` | 아니요 | 우리 팀이면 `true`. 표에서 파란 바탕으로 보이고, 상세 끝이 적용안 링크로 바뀝니다 |
| `kind` | 아니요 | 짧은 분류 태그. 예: `EC2 Compose`, `k3s` |
| `source` | 아니요 | 본 브랜치와 커밋. 예: `develop · 434c6ca` |
| `facts` | 예 | `[이름, 값]` 쌍 4개. 카드 네 장으로 보입니다 |
| `good` | 예 | 잘한 점 2~4개. **앞의 2개가 한눈에 표에 나옵니다** |
| `bad` | 예 | 아쉬운 점 2~4개. 앞의 2개가 한눈에 표에 나옵니다 |
| `checks` | 아니요 | 항목별 판정 `{ item, grade, text }` 목록. `text`는 한두 문장 |
| `take` | 아니요 | 우리가 가져올 것 1~3개. 우리 팀이면 쓰지 않습니다 |

## 판정 값 (`grade`)

`good`(잘함), `ok`(보통), `weak`(아쉬움), `none`(없음), `unknown`(확인 못 함) 다섯 가지만 씁니다.

## 판정표 (`matrix`)

```json
{
  "note": "판정 기준 한 줄",
  "sections": [
    {
      "title": "백엔드: 회원",
      "teams": ["team1", "team2", "team5"],
      "rows": [{ "item": "탈퇴와 개인정보", "grades": ["none", "ok", "good"] }],
      "note": "표 아래 한 줄 설명(선택)"
    }
  ]
}
```

`grades`의 순서와 개수는 그 섹션의 `teams`와 같아야 합니다. 해당 없는 팀은 `teams`에서 뺍니다.

## 적용안 (`apply`)

```json
{
  "summary": ["**1번은 바로 확인**해야 합니다."],
  "groups": [
    {
      "title": "먼저 볼 것",
      "items": [
        {
          "title": "운영 파일 저장소 확인",
          "why": "무엇이 문제인지 → 고치면 어떻게 되는지",
          "ref": "6팀",
          "badge": { "level": "s", "text": "작음" },
          "urgent": true
        }
      ]
    }
  ]
}
```

- `badge.level`: `s`(초록), `m`(파랑), `l`·`warn`(주황). 크기(작음·중간·큼)나 종류(보안·돈)를 적습니다.
- `urgent`: 바로 손대야 하는 항목만 `true`. 주황 테두리가 생깁니다.
- 번호는 그룹을 넘어 이어집니다.

## 다른 팀 장점 적용 (`strengths`, 선택)

넣으면 「다른 팀 장점 적용」 페이지가 생깁니다. 다른 팀이 잘한 점을 우리 코드와 대조해 AS IS → TO BE로 보여 줍니다.

```json
{
  "note": "부제 한 줄",
  "summary": ["**가져올 것 5개**입니다."],
  "rows": [
    { "status": "todo", "title": "장점 이름", "ref": "8팀 · 1팀", "badge": { "level": "m", "text": "중간" },
      "asis": "우리 지금 모습", "tobe": "가져오면 바뀌는 모습" },
    { "status": "have", "title": "장점 이름", "ref": "2팀", "asis": "우리도 이미 이렇게 함" }
  ]
}
```

- `status`: `todo`(가져올 것)·`have`(이미 갖춘 것). `todo`는 `tobe`가 있어야 합니다.
- `asis`·`tobe`는 70자 이내. `asis`는 코드로 확인한 것만 씁니다.

## 종합 점수 리포트 (`rubric`, 선택)

`rubric`을 넣으면 `build.py`가 기존 `template.html` 대신 [`template-score.html`](template-score.html)을 씁니다. 사이드바의 「기수 전체」에 점수 순위·채점 기준 페이지가 생기고, 팀 상세 맨 위에 점수판(순위·총점·레이더·축별 체크리스트·8팀 분포)이 붙습니다. `rubric`이 없으면 기존 양식 그대로입니다.

완성도 루브릭은 [`rubric-completeness.json`](rubric-completeness.json)에 있습니다. 그대로 `rubric`에 넣고 `summary`만 덧붙입니다.

```json
"rubric": {
  "note": "부제 한 줄", "summary": ["점수 순위 맨 위 결론"], "rules": ["채점 기준 맨 위 규칙"],
  "axes": [{ "id": "feature", "name": "핵심 기능 범위", "short": "핵심 기능", "weight": 20,
             "items": ["확인 항목 1", "2", "3", "4"], "cap": "상한 조건(선택)" }]
}
```

팀마다 `scores`에 모든 축을 적습니다. 찾지 못한 항목도 `ok: false`로 적습니다.

```json
"scores": {
  "feature": { "items": [{ "ok": true, "ev": "OrderService.java:42" }, { "ok": false }, { "ok": true, "ev": "…" }, { "ok": false }],
               "cap": "상한을 건 이유와 근거(있을 때만)" },
  "consistency": { "na": true, "why": "서비스 하나로 된 구조" }
}
```

- 가중치 합은 100이어야 합니다. 축마다 확인 항목은 4개입니다.
- `ok: true`는 근거 `ev`(파일:줄)가 있어야 합니다. 없으면 `build.py`가 멈춥니다.
- 축 점수는 충족 개수(0~4)이고, `cap`이 있으면 최대 1입니다. 판정은 4개 잘함, 2~3개 보통, 0~1개나 상한은 아쉬움입니다.
- `na`(해당 없음) 축은 빼고, 남은 가중치로 100점 환산합니다.

## 설계 선택 (`decisions`, 점수 양식에서 선택)

넣으면 「기수 전체」에 「설계 선택」 페이지(주제별)가 생기고, 팀 상세 끝에 「설계 선택」(팀별)이 붙습니다. 점수와 섞지 않습니다. 선택 지점 목록은 [`decisions-topics.json`](decisions-topics.json)입니다.

```json
"decisions": { "note": "부제", "summary": ["결론 한 줄"], "topics": [{ "id": "event", "name": "이벤트 발행", "options": ["아웃박스", "커밋 뒤 발행"] }] }
```

팀마다 `decisions`에 주제별로 적습니다. 빠진 주제는 「확인 못 함」으로 보입니다.

```json
"decisions": { "event": { "choice": "아웃박스", "considered": ["커밋 뒤 발행", "아웃박스"], "why": "문제 → 그래서 고른 것", "src": "PR #123", "ev": "경로:줄" } }
```

- `choice`는 코드로 확인한 것입니다. `considered`는 글로 남은 선택지만 넣고, 없으면 비웁니다.
- `why`는 70자 이내 한 문장입니다. `why`가 있으면 `src`(문서·PR·커밋·주석)가 있어야 합니다. 근거가 없으면 비워 「이유 기록 없음」으로 둡니다.

### 항목 필드 더 보기 (종합 점수)

| 필드 | 뜻 |
|---|---|
| `checked` | 「모든」 항목에서 확인한 개수. 예: `"12/12"` |
| `why` | 미충족의 근거 종류. `반례`·`없음`·`미확인` |
| `rule` | 적용한 판정 사례 번호. `rubric.rulings`에 있어야 함 |
| `defect` | 결함 사냥이 찾은 반례. 있으면 `ok`는 false |
| `via` | 변호로 충족이 된 항목이면 `"변호"`. 리포트에 「변호 단계에서 충족으로 확인」이 보임 |

`rubric.rulings`는 `{ "id": "R1", "target": "대상", "rule": "기준 문장", "example": "예" }` 목록이고, 「채점 기준」 페이지 끝에 보입니다.
