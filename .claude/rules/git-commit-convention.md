[Conventional Commits 1.0.0](https://www.conventionalcommits.org/ko/v1.0.0/)을 따릅니다. 설명과 본문은 한국어로, 타입과 스코프는 영어로 작성합니다.

## 형식

```
<타입>[(스코프)][!]: <설명>

[본문]

[꼬리말]
```

- 타입 뒤에 콜론과 공백(`: `)을 붙이고 설명을 씁니다.
- 설명은 한 줄로 짧게, 마침표 없이 씁니다.
- 본문과 꼬리말은 선택이며, 앞에 빈 줄 하나를 둡니다. 본문에는 무엇을, 왜 바꿨는지 씁니다.

## 타입

| 타입 | 용도 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변화 없는 코드 구조 개선 |
| `perf` | 성능 개선 |
| `test` | 테스트 추가, 수정 |
| `docs` | 문서 수정 |
| `style` | 포매팅 등 동작에 영향 없는 변경 |
| `build` | 빌드 설정, 의존성 변경 (`build.gradle.kts` 등) |
| `ci` | CI 설정 변경 |
| `chore` | 그 밖의 잡무 (설정 파일 정리 등) |
| `revert` | 이전 커밋 되돌리기 |

## 스코프

변경된 영역을 괄호 안에 명사로 적습니다. 선택이지만 영역이 분명하면 붙입니다.

- 예: `feat(member): 회원 가입 API 추가`, `fix(security): H2 콘솔 접근 허용`

## 호환성을 깨는 변경 (BREAKING CHANGE)

API 응답 형식 변경처럼 기존 사용처가 깨지는 변경은 반드시 표시합니다. 둘 중 하나 이상을 사용합니다.

- 타입(또는 스코프) 바로 뒤에 `!` 표시: `feat(api)!: 회원 응답 필드명 변경`
- 꼬리말에 `BREAKING CHANGE: <설명>` 작성 (`BREAKING CHANGE`는 반드시 대문자)

## 꼬리말

`토큰: 값` 형식이며, 토큰의 공백은 `-`로 대체합니다 (`BREAKING CHANGE`만 예외).

- 예: `Refs: #123`, `Reviewed-by: 홍길동`, `Co-Authored-By: ...`

## 예시

```
feat(member): 회원 가입 API 추가

이메일 중복 검사 후 회원을 저장한다.
비밀번호는 BCrypt로 암호화한다.

Refs: #12
```

```
build: Checkstyle 플러그인 추가

캠퍼스 핵데이 Java 컨벤션 규칙을 원격 URL로 참조한다.
```

```
refactor(order)!: 주문 상태 enum 값 변경

BREAKING CHANGE: ORDERED 상태가 PLACED로 바뀌어 기존 클라이언트 수정이 필요하다.
```

## 커밋 단위

- 하나의 커밋에는 하나의 목적만 담습니다. 기능 추가와 리팩터링이 섞이면 커밋을 나눕니다.
- 여러 타입에 걸친 변경이라면 가능한 한 커밋을 분리합니다.
